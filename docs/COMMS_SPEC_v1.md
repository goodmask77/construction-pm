# GROUN:D 統一通訊、AI 助手與決策中心：CC 執行規格 v1

日期：2026-10-10（Asia/Taipei）
用途：交給 CC 查核現有程式、制定遷移方案並分階段實作。這是執行規格，不是可直接執行的 shell，也不是已完成開發的聲明。
依據：本次完整可見對話的需求與決策。涵蓋導航、產品成本、AI 討論、錄音會議、DD、夥伴問答、多 LINE／IG／FB 通訊、內部聊天室／留言板、桑 App 移轉。未查閱現有程式或先前獨立 MD/XLSX 的內容，不得聲稱已符合它們。

## 0. 給 CC 的開工指令

將使用者的主 App 建立為公司共同入口。桑的 App 最終結束，既有資料與串接先移轉、驗收，再停用。DD、App AI 助手共用服務、資料與對話紀錄；各品牌官方 LINE、IG、FB 訊息集中收發。所有夥伴與 DD／App AI 的工作對話也進入同一通訊中心，授權人員可共同介入回覆。

先讀 repository 的 AGENTS.md 和現有架構；列出已完成／需改造／缺少／外部阻塞項，再在既有 App 實作。保留現有功能與資料身份，不另起一套孤立資料庫。例行且可逆的實作決策自行處理；憑證、帳號授權、平台審核或正式停用舊服務若未具備條件，明確記錄阻塞並繼續可完成工作。不可只有建議、圖片或假資料；假資料僅限標明的預覽，正式功能需接真實資料。

## 1. 最終目標與邊界

1. 手機與電腦都可查看及回覆公司對話，不必逐一切換官方帳號。
2. 一般工作問答使用單 AI，重要議題可選三家 AI 獨立回答、互相詰問、比較、提出行動。
3. 公司記憶是可保存、檢索、版本化的資料；不是宣稱模型自動永遠記得一切。
4. AI 原文、摘要、正式決策分開；CC 的判斷不能冒充三家共識。
5. 真人會議可錄音、轉錄、整理紀錄，確認後連到任務與公司知識。
6. 全體夥伴可問公司工作的事情，但只能取得其有權限的資料。
7. 外部客服、廠商、招募、內部工作問答共用通訊基礎，依權限與用途分開視圖。
8. 不保證零當機、全部歷史可匯入或全部平台能力一致；缺乏資料、失敗、逾時須明確顯示。

## 2. 全 App 導航與整合

主選單分工作區，不再把所有功能平鋪同一層。以下為建議歸屬，CC 依現有路由保留深連結並更新導航：

|工作區|功能|
|---|---|
|首頁|今日工作、待辦、待處理、常用捷徑|
|門店營運|工作站 SOP、班表、異常與回饋、叫貨／採購／盤點入口|
|任務協作|任務板、專案、行動項目、貢獻排行|
|產品與成本|總覽、產品與食譜、物料庫、廠商與報價、菜單與定價、耗損紀錄|
|經營分析|銷售與跨產品成本／毛利分析|
|通訊中心|統一收件匣、內部聊天室、留言板|
|AI 中心|工作問答、AI 會議室、決策與紀錄|
|團隊與資源|夥伴名冊、文件庫、外部工具|

通知放鈴鐺，設定與問題回報放帳號／管理選單。電腦用側欄工作區＋區內分頁；手機用首頁、今日工作、通訊、更多，常用捷徑可自訂。上列為功能归屬，不要求八個入口全部常駐手機。會議、對話、任務從不同頁引用同一筆資料，不能複製成不同版本。

### 2.1 產品與成本的共用資料

- 模組名稱採「產品與成本」。品牌／門店切換與搜尋統一。
- 待處理事項集中總覽，不藏在物料庫；廠商有獨立分頁，不藏在成本總覽。
- 物料包含食材、包材、耗材，保存規格、基本單位、採購單位換算、價格歷史與生效日。
- 物料與廠商為多對多供貨關係，保存規格、報價、有效日期，不能單一廠商欄位取代全部報價。
- 產品／食譜引用物料與半成品食譜；半成品引用不得形成循環。保存產出量／單位及版本。
- 產品頁分基本資料、食譜與製作、成本與毛利、相關紀錄。製作含照片／影片、上下一步、對應材料與計時。
- 進價異動可重算目前標準成本，但保留歷史成本／配方快照與使用的價格來源。
- 製作耗損率與實際報廢分開，定義公式以避免重複計算。缺單價、缺換算、缺產出量要標示成本不完整，不能默認為零。
- 菜單為產品在品牌／門店的販售與定價視圖；包材為物料分類。採購、叫貨、盤點引用共用物料與廠商，禁止另建副本。
- 食譜給員工的製作視圖與管理者的成本視圖分權限。SOP 的門店開收班、清潔等流程與食譜製作分工。

## 3. 通訊中心：統一收件匣

### 3.1 接入來源

|來源|要求與限制|
|---|---|
|AB 官方 LINE|各自帳號／channel 授權、憑證、webhook|
|GD 官方 LINE|同上，保留既有 DD 或其他機器人流程|
|招募官方 LINE|指公司管理的官方 LINE；104 平台內建訊息是另一個待查串接|
|廠商 LINE|官方帳號收到的私訊／已加入的群組；個人 LINE 私聊不能靠官方 API 自動接入|
|IG 私訊|專業帳號、訊息授權、相應 API 路徑／權限|
|FB Messenger|粉專訊息、相應權限／存取憑證；非個人 Messenger|
|夥伴與 DD 的工作問答|員工身分綁定、保存訊息與 AI／人工答覆|
|夥伴與 App AI 的工作問答|與 DD 共用對話與服務，可在管理收件匣介入|

多平台底層第一期就建立；LINE 先驗收，Meta 再接。每筆對話綁定 platform、channel_account_id、external_thread_id；外部參與者 ID 必須加平台／帳號命名空間，不能只靠名稱或裸 ID 合併。相同聯絡人跨品牌／平台可人工關聯資料卡，但保留各條對話與發送身分。

### 3.2 收件匣視圖

- 頂部品牌／用途篩選：全部、AB、GD、招募、廠商、夥伴問答；再提供平台篩選：LINE、IG、FB、App。
- 桌面：對話列表／訊息內容／可收合資料側欄。手機：列表進單一對話，資料在抽屜。
- 列表含來源帳號標籤、最後訊息、時間、未讀數、狀態、負責人、釘選。
- 狀態：未處理、處理中、待對方回覆、已結案；與個人的已讀／未讀分開。
- 搜尋對話、聯絡人、群組、可見訊息、備註；權限先過濾再查詢。
- 對話頂部顯示品牌、來源帳號、私訊／群組、處理人、目前 AI／人工模式。
- 輸入區明確顯示「以 GD 官方 LINE 回覆」或「以張良瑋身分回覆夥伴」。不得由前端任意提供 token 或繞過來源綁定。
- AI 回答、人工回覆、內部備註不同樣式和標籤。內部備註永不送到外部平台。
- 人工訊息可紀錄實際操作人；外部接收者看到的平台身分仍是官方帳號。
- 支援文字優先；圖片、語音、影片、檔案依平台能力逐項實作，未支援明確提示。
- AI 草擬、摘要、分派、轉任務、連廠商／客戶資料卡。外部 AI 自動發送預設關閉。

### 3.3 夥伴問答共同回覆：本次新增的明確需求

所有夥伴跟 DD／App AI 的「公司工作對話」集中顯示，讓管理者和被授權處理人共同回覆，作為未來統一溝通管道。

- 員工首次使用前清楚顯示「公司工作問答會保存，授權管理人員可查看與介入」，不得呈現為只有本人與 AI 可看的私人聊天。
- 「集中顯示」不等於全員可以看所有人的對話。管理者按角色看全部或範圍內工作對話；普通夥伴只看本人及被邀請的討論。
- 人資／薪資等敏感主題路由至受限處理群，不能因一般客服權限而可見。
- 收件匣可人工接手、邀請協作者、留下內部備註、請 AI 查詢、恢復 AI 模式。
- 人工接手期間暫停 AI 對外自動答覆；已在生成中的答案送出前再次檢查模式／版本，防止雙重回答。
- App 回覆同步送到原 LINE DD 對話；LINE 回覆寫回同一紀錄。跨 App／LINE 接續需綁定身分並明確選擇主題，不把所有個人問題強行串成一條。
- 保留 user、assistant_ai、human_agent、internal_note、system_event 角色與審計資料，不能把人工回覆偽裝成 AI。

### 3.4 內部聊天室與留言板

- 聊天室：私訊、工作群組、任務關聯討論、附件、未讀、提及、通知、搜尋與成员管理。
- 留言板：公告／議題、回覆串、釘選、分類、可見範圍、已讀確認及版本。
- 即時更新不等於背景通知。分開驗證 App 開啟時同步、背景／鎖屏提醒；PWA／平台不支持的情況須顯示，採可用替代通知。
- 共用訊息與附件基礎，但公告已讀確認、聊天未讀、收件匣待處理是三種不同狀態。

## 4. 共用 AI 助手與公司知識

DD／App 是入口，後端共用 AI orchestration、權限、工具、知識檢索、對話儲存。不要在 DD、App 各維護一份公司記憶。

### 4.1 工作問答

- 一般問題預設單模型，可按政策升級三模型；不要每句話都呼叫三家。
- 食譜／SOP／決議／文件：檢索有效版本，附標題、版本、更新時間與深連結。
- 庫存、進價、任務進度：讀授權資料庫／工具的即時結果，不能僅靠舊向量摘要回答。
- 區分公司事實、AI 建議、待確認；沒依據則指出缺資料，不編公司規則。
- 知識來源有討論中、待確認、已生效、已取代；一般問答優先已生效。草稿僅在明確要求討論草稿時納入並標示。
- 發布、修改、取代、刪除或權限變更需更新索引／快取；回答可查到使用的來源版本。無權資料不能先送給模型再在輸出遮蔽。
- 工具寫入或對外發送採明確指令、角色權限與操作紀錄；收到客人／廠商文字不等於取得修改公司資料的授權。

### 4.2 上下文與可檢查的記憶

保存完整訊息；每次帶入主題、近期原文、較舊摘要、有效決策與相關來源。摘要保存涵蓋到哪筆訊息，不得覆蓋原文。關鍵數字、承諾、決議必要時回查原文。

群組依回覆訊息、提及、明確主題區分；「那個方案」不確定時釐清。提供新主題／繼續主題入口。AI 會議室可查看實際帶入的背景與來源，敏感內部提示與秘密不公開。保存歷史不代表每次把全部歷史送給模型。

### 4.3 DD 穩定性

- webhook 驗簽、保存事件、去重後盡快確認接收；耗時工作進背景佇列。
- 長問題可先確認「已收到，正在查詢」，再按平台許可送結果。UI 顯示 queued／running／completed／failed／cancelled。
- 有限重試、指數退避、逾時、死信佇列、可重跑、錯誤告警；追蹤收訊、資料查詢、模型、發訊哪段出錯。
- 以事件 ID／唯一鍵處理 webhook 重送。發訊重試依各平台冪等能力，結果不明時先核對，不能盲目重送。
- token 更新／失效、權限撤銷、平台限制分開呈現。API 成功不等於對方已讀，狀態不能造假。
- 模型失敗可按政策換備援，紀錄實際模型，不聲稱三家全部完成。資料查詢失敗不能用幻覺補答案。

## 5. AI 會議室（三家討論）

功能：手機／電腦文字或語音提問，主題與附件，邀請可見成員，持續追問，保存原文與決策。

執行階段：
1. 固定共同問題、背景、限制、資料版本，保存 input snapshot。
2. 三模型獨立回答，第一輪不看其他模型／CC 的答案。
3. 交叉詰問：檢查假設、矛盾、遺漏、支持理由，預設一輪，可手動追加。
4. 融合報告：共同結論、分歧、尚未驗證事項、選項、主持者建議。未回覆／不同意不得算入共識。
5. 行動建議：內容、建議負責人、期限、依賴；未指定不捏造。
6. 自動摘要／會議草稿；有權人確認後發布決策、選擇建立任務／交 CC。

三家供應商／模型可設定，不在本文件硬編最新型號。UI 顯示實際供應商、模型、階段、開始／結束、錯誤／部分完成與費用估計。設定輪數、token／金額上限與停止按鈕。中止保留已完成內容。

原始模型回應由服務直接保存，CC／主持者不覆寫；保存每次輸入、參數、來源、輸出和時間。摘要主張連回原回答片段；人工修訂摘要保留版本。主持者既提出方案又統整時也要標識其判斷，不投票冒充驗證。

## 6. 真人錄音會議與紀錄

- 新建會議：標題、參與者、議題、品牌／門店、可見範圍。
- 錄音前告知與會者，顯示錄音狀態；暫停／繼續／結束，分片保存與上傳進度，重載／離線有可恢復設計。
- 驗證手機瀏覽器／PWA 的麥克風、來電、鎖屏、切背景限制，不能承諾背景永遠持續錄音；中斷清楚提示並保留可救片段。支援錄音檔上傳作替代。
- 第一版錄音後轉錄與整理，再做即時轉錄／按鈕請 AI 加入；AI 預設安靜，不強迫三模型每句介入。
- 逐字稿含時間戳；講者辨識不確定標示未知並可修正，不捏造講者。
- 固定產出：討論重點、不同意見、已確認決議候選、待確認、行動項目、負責人／期限（未說明就未指定）。
- 摘要連回逐字稿／錄音時間。草稿經主持者／授權人確認成正式紀錄，未確認不能當公司規則。
- 行動項目逐項確認後建任務，保留來源連結與去重，修改紀錄不會偷偷改已派出的任務。

## 7. 決策、任務與 CC 執行交接

決策存主張、理由、適用品牌／門店、核准者、生效日、狀態、来源、被取代關係。新決策取代舊版本而非刪掉歷史。工作問答引用現行版本。

交 CC 的 task packet 含問題、已確認決策、限制、驗收、附件／來源版本、權限、任務 ID。沿用既有「DD 收件匣→CC 執行」流程並加狀態、領取鎖、進度、結果、錯誤回寫；不能多人領同一任務或重跑造成重複操作。討論建議不自動授權部署／付款／對外發訊。

## 8. 資料模型（概念草案，先對照現有 schema）

|實體|核心欄位／關係|
|---|---|
|organization／brand／store|公司、品牌、門店與資料範圍|
|members／roles／identity_links|員工、角色、平台 ID 綁定與驗證|
|channel_accounts|平台、帳號外部 ID、品牌、用途、連線狀態、秘密引用|
|contacts／contact_links|客戶／廠商／候選人、人工驗證的平台關聯|
|conversations／participants|來源帳號＋外部 thread、內外部類型、範圍、處理人、模式|
|messages／attachments|原始內容、發送者角色、平台事件 ID、時間、引用、附件、發送狀態|
|read_markers／assignments／notes|個人已讀、待處理狀態、分派、內部備註|
|ai_runs／model_responses|共同輸入快照、階段、模型、原文、使用量、失敗|
|meetings／recording_segments／transcripts|會議、錄音片段、時間戳逐字稿、講者|

|jobs／inbound_events／outbox／audit_logs|背景工作、去重事件、發送佇列、稽核|
|materials／supplier_offers／recipes／products|共用產品成本實體與引用|

每個重要物件有穩定 ID、created_at／updated_at、來源、organization 與必要範圍。對話外部唯一鍵涵蓋平台和來源帳號。附件保存在受控儲存，簽名連結短效；秘密僅伺服器存放。資料庫權限與 API 權限都要檢查，若使用 Supabase 則落實相應 RLS。模型原文追加保存；需要移除敏感資料時走授權刪除／遮罩及審計流程，不假裝絕對不可刪除。

## 9. 平台串接限制與資料移轉

- LINE：多帳號獨立 channel 憑證／驗簽；整合既有 webhook 處理，避免換 URL 後 DD 停收。群組需官方帳號加入並開啟相關設定；每群官方帳號數量等限制以當時文件查核，不假設所有帳號都可同時加入。不能透過官方 API 拉取個人 LINE 私聊或完整舊歷史。
- Meta：按選定登入／API 路徑申請權限、webhook 和審核；一般測試角色可用不代表一般客戶可用。訊息回覆窗口、允許例外、附件及歷史可取得範圍由 connector 層查核並呈現，不把 LINE 規則照搬。
- 原平台管理介面發出的人工訊息是否能完整同步，必須實測各平台事件／歷史能力；不能宣稱所有訊息雙向自動同步。切換後以 App 為主要回覆入口，其他入口限制標示。
- 桑 App：盤點資料庫、帳號權限、附件、身分、廠商／群組 mapping、來源事件 ID、憑證、工作佇列、DD 路由、舊回覆紀錄。先備份，mapping 可回溯，秘密透過安全移轉。
- 先導入歷史，再以可控切換／事件鏡像驗證新系統；鏡像時只有一方擁有發送權。核對數量、時間、附件與抽樣對話；通過收發與回滾演練才停舊 App。不可兩套同時自動回覆。

## 11. 必要驗收情境

1. AB／GD 同時收到訊息：同頁顯示，回覆各回原帳號，跨帳號同名者不混線。
2. 官方帳號已在廠商群組：群訊正確進來／回群；未加入群組不假造同步。
3. 同一 webhook 重送三次：只一筆訊息、一個 AI 作業及一次外發。
4. 夥伴 LINE 問食譜、App 繼續追問：在選定同主題可接續，附有效來源。
5. 管理者人工接手：AI 已生成待送的回覆被阻止，員工看到真實人工身分；内部備註不外發。
6. 一般夥伴不可查看他人受限問答／薪資；未授權資料不进入搜尋、模型上下文或來源連結。
7. 新進價／SOP／決策發布：回答更新；被取代版本不能默認現行，引用版本可追溯。
8. 資料缺漏／工具逾時／模型失敗：明確提示而非編答案；重試不造成重複發送或任務。
9. 三模型討論一個失敗：顯示部分完成；原文保存，共識不包含失敗模型；可單獨重跑。
10. 摘要修改不改模型原文；可從共識／分歧追到原文和背景快照。
11. 會議錄音中斷／上傳失敗：已保存片段可恢復，狀態准确；逐字稿摘要可點回時間。
12. 未確認會議草稿不成公司規則；確認後建立任務一次，負責人／期限未指定不造假。
13. Meta 窗口外／權限失效：阻止不允許的發送並解释原因，不偽造成功。
14. 手机列表／對話／錄音／AI 討論可操作；重載能看历史；背景通知另測。
15. 桑 App 移轉：原 ID mapping、附件、對話抽查一致；可回滾，只有一方外發。
16. 物料價格更新影响相關食譜目前成本，歷史成本不变；缺單價／換算不能顯示完整毛利。

## 13. 不得自行縮減或誤解的需求

- 多帳號與夥伴工作問答都要集中，不是只做廠商 LINE 頁。
- 「AI 討論」「真人錄音會議」「工作問答」都是範圍；不是只做單模型聊天視窗。
- App 與 DD 共享資料、上下文與有效決策，不是互相貼一份摘要便宣稱整合完成。
- 三家原文與送入背景可檢查；統整不能覆寫原文或強迫共識。
- 公司所有資料有各自权限與有效版本，不能宣稱 AI 全知。
- 共同回覆是授權人員共同處理，不能默認把所有夥伴敏感問答公開給全員。
- 桑 App 會結束，但資料和機器人先遷移驗收；不要先停舊系統。
- 本規格覆盖功能與验收；詳細欄位、API、migration 需以實際 repository 查核後落地，不能憑本文件臆造現有狀態。
