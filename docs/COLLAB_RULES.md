# 協作鐵則：四人分區共編新殼 abgd（張良 2026-10-14 定，試行版 v2）

適用：新殼 abgd（Next.js＋TypeScript，一個 GitHub 私有 repo、一個 Vercel 專案、Supabase，全部在 goodmask77 名下）。
參與：張良（外框／共用）、Belle（財務）、阿桑（營運）、小夏（包場 EM）；每人用自己的 AI（Claude Code／Codex）寫程式。
依據：大公司公開做法（Google、Shopify、Uber、GitHub、Meta、Stripe、Vercel、Anthropic）；三家查證與審查紀錄見 `docs/TEAM_ISOLATION_3AI_2026-10.md`。
這份是規則，不是建議。試行中遇到問題，張良決定後改這份，版本號 +1。
搭配：速度鐵則 `docs/PERF_RULES.md`、搬遷鐵則 `docs/MIGRATION_RULES.md`。

> **先講清楚能做到什麼**：個人帳號的 repo，協作者一律「整個 repo 可讀可寫」，GitHub 不能依資料夾鎖權限。
> 所以分區靠的是「**合併前必須由該區負責人核准＋自動檢查**」，不是「別人改不到」。程式寫錯能一鍵退回；資料庫另有一層保護（第五節）。

## 二、改程式的流程（每個人、每次都一樣）

1. 開一條新分支，名字 `區/做什麼`（例：`finance/月報表`）。一件事一條，**1~2 天內合併**。
2. 同一台電腦同時開多個 AI，每個 AI 用自己的 worktree（獨立資料夾），不共用。
3. 開工前先把最新的 main 拉進來。
4. 改完開合併申請（PR），寫：改了什麼、哪一區、速度量測（只量受影響的頁面，照 PERF_RULES）、有沒有動資料庫。
5. 系統自動跑檢查（第三節）＋產生預覽網址。
6. 核准人用預覽網址點過後核准（純文字／排版小改，檢查全過可只看截圖）。
7. 合併 → main 自動再跑一次檢查 → 正式站自動部署。

## 三、合併前自動檢查（沒過不准合併）

| 檢查 | 擋什麼 |
|---|---|
| 建置＋型別檢查＋語法檢查（Next.js 16 build 不再自動跑 lint，CI 要另外跑） | 寫壞的程式 |
| 分區檢查：動到哪些區、有沒有跨區寫入、有沒有動高風險檔 | 越界修改 |
| 關鍵流程測試：金額計算、角色越權（例：營運帳號讀不到財務） | 算錯錢、資料外洩 |
| 資料庫變更檢查：migration 只能新增，不准刪表、刪欄、改欄名 | 資料庫被改壞 |
| 速度檢查：首次下載大小（照 PERF_RULES） | 變慢 |
| 機密掃描（CI 自裝 gitleaks；GitHub 個人方案不會自動掃） | 金鑰、密碼、手機、身分證進 repo |

**main 保護設定（GitHub Pro 傳統分支保護）**：必須 PR、至少 1 位核准、必須程式碼負責人核准、**有新推送就作廢舊核准**、**最後一次推送須由他人核准**、必要檢查要過、禁止強制推送與刪除、**管理員也不能略過**。
「合併前分支必須最新」**先不開**（四人會互相卡著重跑），改成合併後 main 自動再檢查，失敗就退回。

## 四、部署（只有一條路）

- **正式站只從 main 自動部署。** 任何人（含 CC）不從自己電腦執行正式部署。
- 環境變數：**只有張良（CC 代操）能在 Vercel 改**，不在 repo 裡。
- 三位夥伴的預覽網址（**開工第一天實測決定**，Vercel 官方兩份文件說法不一致）：
  - 先試：三位不加入 Vercel，推程式看會不會自動產生預覽（官方 Git 文件寫個人帳號 repo 不檢查席位）。
  - 不行就改：三位加入 Vercel 團隊（每人 US$20/月），或由 CC 代發預覽。
  - 預覽站有登入保護，非成員要用「分享連結」才打得開；開工時一起實測。
- 正式站壞了：**先一鍵退回上一版**（Vercel Instant Rollback，CC 執行），再修。
  - 退回後 Vercel 會**暫停自動上線**，修好合併後要按「Undo Rollback」恢復，否則之後都不會上線。
  - 退回不會退資料庫、外部系統，也不會改回目前的環境變數設定。
- 功能開關：等外框穩定後再加；在那之前，沒做完的功能不合併。

## 五、資料庫

- 每區只寫自己的 schema；`core` 只有外框能寫。
- **先講清楚**：四區的伺服器程式共用同一把管理金鑰（service role），這把金鑰會略過權限規則（RLS）。所以「只寫自己的 schema」靠的是程式審查＋自動檢查，不是資料庫自己擋。給使用者用的讀寫一律走登入身分＋RLS，不用管理金鑰。
- 資料表結構只能用 `supabase/migrations/` 裡的檔案改，走 PR；**正式庫的 Supabase 後台不准手動改表**。
- **誰套用、什麼順序**：PR 核准後，**由 CC 在張良電腦上先套到正式庫，再合併程式**（因為只准新增，先套資料庫不會讓舊程式壞）。正式庫密碼只在張良電腦與 Vercel 正式環境，**不放 GitHub Actions**。
- 改結構一律「先加後減」：先加新欄位 → 新舊兩邊都能用 → 搬資料、確認 → 最後另一個 PR 才刪舊的（張良核准）。
- RLS 建表當下一起寫：讀、新增、修改、刪除四種都要設，view 與函式也要檢查會不會繞過權限；沒有 RLS 的表不准合併。
- **預覽站與自動檢查只接一個共用的測試專案**，裡面只放假資料；**禁止把正式資料匯進測試庫**。
- 預覽站的金流、LINE、寄信、簡訊也要接測試帳號或關掉，不能真的扣款或發訊息。
- GitHub Actions 只放測試庫金鑰（有寫入權的人改 workflow 就能印出機密）。
- 備份：正式專案用 Supabase Pro（每日備份保留 7 天）；上傳檔案（Storage）另寫備份腳本。**上線前演練一次還原**（含登入、權限、檔案、帳務核對），之後每季一次。

## 六、衝突怎麼處理

- 只動自己區的衝突：自己處理，處理完重跑檢查。
- **跨區衝突：停下來**，在 PR 標註兩區負責人，兩人確認後才解。**不准讓 AI 自己「全部選我的版本」**。
- 新裝程式套件：會改 `package.json`，一律張良核准；PR 說明寫理由。

## 七、AI 提醒（不是關卡）

- 每個人的 AI 開工時設定自己是哪一區（`ABGD_ZONE=finance` 等）。
- Claude Code：repo 內建 hook，寫入（含用 Bash 指令寫檔）自己區以外的檔案時**跳出提醒並擋下**；但這可以被關掉，所以**真正的關卡是第三節的自動檢查＋負責人核准**。
- Codex：讀 `AGENTS.md` 同一套規則。
- AI 一律不拿正式庫金鑰、不執行正式部署、不改把關規則。

## 八、AI 審查（分兩階段）

| 階段 | 做法 |
|---|---|
| 第一階段（開工第一個月） | 一般 PR：一家 AI 審查留意見；高風險（財務金額、金流、權限、資料庫、外框、套件）：三家各自審。**合併一律由核准人親手按** |
| 第二階段（張良確認穩定後才開） | 「只動自己區、純畫面或文字、檢查全過、AI 審查沒意見」→ 自動合併；有疑慮 → LINE 私訊核准人附理由 |
| 永遠人工 | 財務金額、金流、權限、資料庫結構、外框、套件、把關規則 |

## 九、私有、機密與帳號安全

- abgd repo 一律私有。
- 程式碼、註解、文件、commit 訊息不准寫真實個資；測試用假資料。
- 金鑰只放 Vercel 環境變數，不進 repo、不貼在對話裡給 AI。
- **goodmask77 是全部系統的唯一擁有者**：GitHub、Vercel、Supabase 都開兩步驟驗證，備援碼印出來放保險箱；之後評估加一位備援擁有者。
