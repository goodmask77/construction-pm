## 第一輪 OpenAI

## 1｜程度：功能超前，可靠性落後
- 四個半月做到跨店 POS、LINE、排班、成本與行銷整合，**功能廣度已超過兩店必要範圍**；但審查包不足以證明生產可靠性，1579 次提交不是品質指標。
- 超前：統一收件匣、營運看板、物料成本追溯，直接服務管理。
- 過度建設：聊天、積分遊戲化、素材抓取、預測多期並進，超過目前維護承載力。
- 明顯不足：交易一致性、自動測試、復原演練、外部接口失效處理。**下一階段應減少功能增量，不是整套重寫。**

## 2｜功能取捨
**停／合併／砍**
1. 暫停預測 P2/P3、耗損自動採購：先證明資料與基礎預測可靠。
2. 合併互評、積分、排行榜、商城入口：避免多套激勵規則增加管理負擔。
3. 合併各處 AI 顧問的後端能力：保留不同入口，但共用權限、工具與資料算法。
4. 暫停 Pinterest 自動抓取擴充：尚無證据顯示比核心營運更有價值。

**補**
1. 金流／點數流水、冪等與對帳：防重複付款、重複加點。
2. 高風險動作確認與稽核：付款須顯示對象、金額，不能只相信模型指令。
3. 核心回歸測試與備份還原：讓老闆不必每次重測整套。
4. 資料新鮮度、接口失敗告警與人工替代流程：避免拿過期資料做決策。

## 3｜架構：漸進改造，不換整套
- **先測試與權限邊界，再拆檔。**測試鎖住既有行為，避免拆完功能變掉。
- 拆分順序：DD 的資料讀取／動作執行 → mail-sync 的收信／營運／成本／設定 → App 頁面。先抽模組、保留舊接口，再逐步換路由；不拆微服務。
- KV 文件立即加入口 schema、版本及驗證。金流、點數等一致性核心逐步搬 Supabase 真表，用交易、唯一約束、流水及對帳；**不是全部 KV 搬家**，快取與一般文件可留。
- /prep 不必換框架：每頁一檔尚可維護，先補共用元件、版本管理與測試；新複雜頁再評估 React。
- DD 的 47k 字改成穩定規則＋按身分、問題取資料；目的是減少混淆與越權，不只是省 token。

## 4｜組織：讓流程承擔記憶
- 張良決定需求、驗收與 merge；Claude Code 實作；阿桑負責 boss-api 契約與相容性，不互改對方系統。
- 一張需求卡寫清驗收、資料影響、回滾；PR 必須同步最新 main，通過檢查、預覽與驗收才合併。
- 多 session 按領域分工；共用檔只准一個 session 修改，禁止整檔覆蓋。
- 規格設單一索引與決策紀錄；memory 只是導覽，不是規格真相。
- 一家 AI 常規審查；金流、權限、資料遷移才加第二家獨立審。三家投票不能代替測試。

## 5｜模型：保留高風險配置，別為幾美元折騰
以下判斷採用包內型號、價格，能力仍須實測。
- **DD 留 opus-5-5**：月費很低，現在不值得為省錢換模型。但付款安全靠伺服器規則、確認與冪等，不靠 opus。與 sol 的盲測須包含越權、錯付款、工具誤用；一週雙答不能證明低頻風險。
- 行銷文案、顧問、菜單建檔、食譜匯入、圖像指令維持 **gpt-6.1-sol**。讀秤另用已知重量樣本驗證，低信心要求人工輸入。
- 一般翻譯、摘要用 **luna**，haiku 備援；涉及金額、重要承諾的結果須確認。權限、計算、個資遮罩不用模型決定。
- 生圖維持現有 Gemini 主備；沒有品質、延遲實測理由就不換。
- 品質閘門用 sol＋確定性檢查，重要稿件由 sonnet 複審；「85 分」不是安全保證，仍保留張良核准。
- **fable-5／astra**只用於難解架構、嚴重事故或高風險審查爭議，不常駐、不因此開放自動執行。
- 開發維持 Claude Code；sol 獨立審程式，重點看權限、交易、遷移與測試，而非只評論寫法。

我是由 Google 的 Gemini 系列「gemini-3.8-flash」模型驅動。以下為全盤審查意見：

---

### 1. 程度評估
在 4.5 個月內由一人 AI 交付出此等體量，**速度屬怪獸級，但架構已嚴重「骨質疏鬆」**。
*   **超前**：DD 動作引擎、農業部行情比價、營運報表下鑽。餐飲業能把 AI 深入到即時業務讀寫與報價監控，已超越 95% 同業。
*   **過度建設**：
    1.  自建 Google Chat 式聊天室（內部已有 LINE 群，自建溝通工具是無效益負擔）。
    2.  自建電視菜單匯出引擎與 AI 重繪（變更頻率低，Canva 即可解決）。
    3.  Pinterest 自動抓圖與靈感庫（離直接變現太遠）。
*   **明顯不足**：**「零測試、零事務（Transaction）、零 Schema」**。用 KV 存帳務與任務，且靠前端約定防呆，只要一次並行寫入衝突或網路中斷，帳目立刻破網，老闆看不到程式碼卻隨時可能面對假數據。

---

### 2. 功能調控
#### 【停／合併／砍】
1.  **砍 自建聊天室**：LINE 官方帳號與群組足夠，自建即時通訊只會徒增 WebSocket/長輪詢維護地獄。
2.  **砍 信箱中樞（多信箱 IMAP 爬蟲）**：維護認證與解析極度脆弱，應改用 Zapier 或單一轉寄 Webhook。
3.  **停 Pinterest 圖版自動抓取**：對實體店營業額貢獻接近零，純屬資源浪費。
4.  **合併 菜單出圖與行銷素材庫**：整併入「行銷自動線」，不應作為獨立龐大模組維護。

#### 【補】
1.  **補 交易與點數的 Supabase ACID 表**：自建會員與點數若繼續用 KV，必然發生雙花（Double-spending）與帳差。
2.  **補 逆向 API 斷線警報探針**：inline、NUEiP、POS 皆為爬蟲/逆向，介面一改靜默失效，必須有主動掛掉通知。
3.  **補 營收 vs 菜商叫貨自動勾稽核對**：進貨金額 vs POS 銷售理論耗損對齊，抓出內耗或漏單，這才是老闆最痛點。
4.  **補 核心 API 端點的自動化契約測試（Contract Test）**：防止 Claude Code 每次部署洗掉舊欄位。

---

### 3. 架構體檢與處方
*   **換不換框架？不換。**
    *   前端繼續維持 Vanilla JS（/prep）模式，現階段千萬不要重構引進 Next.js 或 Vite，否則 Claude Code 至少要花一個月排查依賴問題，張良的手測體感會直接歸零。
*   **換不換資料庫？「雙軌制」**。
    *   **KV 留著**：只放暫存、快取、日誌、DD 對話狀態、排班顯示草稿。
    *   **交易/帳務全入 Supabase (Postgres)**：會員點數、財務管理帳、員工薪資、盤點真值，**必須立享有 Schema 的關聯表與 Row Level Security**。
*   **重構優先順序**：
    1.  **立刻拆解 `api/mail-sync.js`（6325行）**：代價約 3 天。改用目錄分流（如 `api/routes/menu.js`），由 index 做路由派發。這檔是隨時引發 Git 衝突的火藥桶。
