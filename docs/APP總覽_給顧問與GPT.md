## 0. 一分鐘背景

- **公司**：一位老闆（張良，身兼財務）經營兩家餐飲店——
  - **GROUN:D**：美式餐飲，用「喬亞 POS」。目前的**主力店 + App 主要戰場**。
  - **A Beach**：海灘餐廳，用「Eats365 POS」。
- **這個 App 不是買的、不是外包的**。它是老闆用「跟 AI 對話」的方式，一頁一頁長出來的**全自營運系統**——POS、訂位、排班、人資、叫貨、財務、SOP、通知全部自己串進來。
- **老闆的風格（很重要，決定了產品長相）**：非技術背景、要「用最少力氣把店管好」、一切**表格化 / 視覺化 / 可勾選**、**資料一致**（同一個數字到處都一樣）、**主動提醒追到底**、對外（廠商群組）**安靜保守不外洩金額**。
- **現在的目標**：把這套「自己店在用、而且真的好用」的系統，變成 **(a) 餐飲業的商業顧問服務**、**(b) 可以賣給別人的產品 / SaaS**。

**三個關鍵設計決策（護城河雛形）**：
1. **串接地獄已經做掉**：每一家 POS / 訂位系統都是逆向工程硬接進來的（喬亞、Eats365、inline、NUEiP 都沒有正式對外 API，是抓登入→換 token→撈資料）。這是最髒、最難、最有價值的部分。
2. **AI 雙邊鐵則**：任何新資料域，**DD（LINE bot）和 App 內 AI 顧問兩邊都要同步接上**，確保「問 AI = 看畫面 = 同一套數字」。
3. **資料一致鐵則**：同一個數字（例如營收、日均）在不同頁面一定用**同一套算法**，不能各算各的。

## 2. 前端 A ──「GD」夥伴 App（/prep＝/ops）＝ 現在主力

- **定位**：給店內夥伴（店長 / 正職 / PT）每天用的手機 App。**PWA**（可加到手機主畫面、像原生 App）。
- **技術**：純前端靜態頁（`public/ops/`），無框架、手刻；分 13 個檔 `p01~p13`。資料全部打後端 `mail-sync.js` 的 `opsboard` 等端點。
- **權限**：伺服器端守門。4 位數登入碼綁定個人身分（`&me=token`），敏感資料（薪資、名冊）主管才看得到；一般夥伴看到唯讀、沒權限的按鈕變灰鎖。
- **店別切換**：頂端 GROUN:D / A Beach 一鍵切，同一套頁面兩家店共用。

- **定位**：桌機為主的「總控台」。原本是工程專案管理，演化成含餐飲全部的多空間後台。

## 4. 後端 & 資料層

- **後端**：Vercel Serverless Functions，資料夾 `api/`。核心是 **`mail-sync.js` 一支巨型檔，約 100 個端點**（用 `?xxx=金鑰` 分流）：營運看板、品項、叫貨、會議、SOP、班表、inline、權限…幾乎全部。
- **其他 api 檔**：`line-webhook.js`（DD 機器人）、`ai.js`（AI 顧問）、`punch.js`（打卡）、`hr.js`/`inline-sync.js`/`em-sync.js`/`boss-sync.js`/`joya-intraday.js`/`eats-rhythm.js`（各外部系統同步）、`push.js`（LINE 推播/計費）、`cron-daily.js`（每日排程）等。
- **資料庫**：Supabase 一張表 `pm_documents`（key-value）。設計上**逐筆存檔 + 月檔**（交易/任務一筆一檔、POS 按月分檔），避免整包覆蓋、支援即時同步。金鑰制存取、RLS 上鎖。
- **排程 cron**：POS 每小時/每 15 分抓盤中、每日日結、NUEiP 出勤每日 22:40、inline 滾動同步、EM 每小時、顧客資料庫每 20 小時重算…**全自動，老闆不用手動匯入**。

## 6. 兩個 AI 分身

- **DD（LINE 機器人）**：老闆/夥伴在 LINE 直接下指令——建任務、查營收、問班表、回報問題、轉需求給開發。全資料域、跨空間操作。
- **App 內 AI 顧問**：桌機後台的對話框，同樣全資料域，偏「深度分析 / 報表問答」。
- **鐵則**：兩邊共用同一份資料、同一套算法。新功能一定兩邊都接。

## 7. 首頁營運儀表板：現況 + 設計建議（你問的重點）

### 7.1 現況（GD 首頁，由上到下）
1. 今日營收大卡（即時/日結，vs 近 7 日均）
2. 今日事項（今天該做的任務/收貨）
3. KPI 三卡：總營收 / 日均 / 總單 ← **剛改成「本月大字＋今年小字」**
4. 每日數據表（可切本月/上月/年，色階）
5. **時段營收熱力圖**（剛加回來）
6. 平日/週末時段 bar、停售動態

### 7.2 現況的問題（給 GPT 討論用）
- 首頁**一屏塞很多表**，偏「資料陳列」，不是「決策導向」。
- **沒有明確分角色**：老闆要看錢和異常、店長要看人和備料、夥伴只想知道今天做什麼——現在大家看同一頁。
- 缺少「**該我行動的事**」聚合（異常/待辦/快違規/庫存見底/訂位爆量）用紅黃綠一眼掃。
- 趨勢偏「看歷史」，較少「**預測/預警**」（雖然後端已有銷量預測引擎，可往前擺）。

### 7.3 設計建議（我的版本，可丟給 GPT 再深化）
一個好的餐飲營運首頁，應該在**一屏內回答三個問題**：

> **① 今天賺多少？ ② 一切正常嗎？ ③ 我現在該做什麼？**

建議版型（由上到下、重要性遞減）：

```
┌─ 北極星區（最大）──────────────────────────────┐
│  今日營收 ▲/▼ vs 同星期均   │  本月累計 / 目標達成%  │
├─ 紅黃綠「要注意」區（第二重要）─────────────────┤
│  ⚠ 異常 3   │ 🔴 快違反勞基法 1 │ 📦 庫存見底 2    │
│  📅 今晚訂位 48 人（大組1）  │ 🚫 停售 2 項        │
├─ 「該我做的事」區（依身分變）──────────────────┤
│  店長：SOP 未完 4 / 待叫貨 / 待簽會議              │
│  夥伴：今天我的 SOP / 今天班 / 備料量             │
├─ 趨勢 & 預測（往下捲才看）────────────────────┤
│  每日數據表 ・ 時段熱力圖 ・ 明日預估營收/備料     │
└───────────────────────────────────────────────┘
```

**設計原則**（符合老闆既有鐵則）：
- **分角色預設視圖**：登入身分決定首頁長相（老闆=錢+異常、店長=人+貨+SOP、夥伴=今天該做什麼）。
- **先給結論再給數字**：每個數字旁邊配「正常/偏高/偏低」的紅黃綠，不用自己心算。
- **可行動**：每張卡能點進去直接處理（補貨、催簽、看是誰快違規）。
- **預測往前擺**：把「明天預估營收 / 建議備料 / 今晚訂位壓力」放顯眼處＝從「看昨天」升級成「準備明天」。
- **一致**：所有數字沿用現有同一套算法與口徑。

## 8. 從我們的溝通：你的想法 vs 我的建議（商業化）

### 8.1 你的產品哲學（從長期合作歸納出來，這其實就是產品的 DNA）
1. **對話即操作**：能用講的就不要點。App 背後站著 AI（DD / 顧問），下指令就完成。
2. **老闆視角，不是工程視角**：按鈕不露內部概念、不丟程式碼、一切白話。
3. **資料一致是信仰**：同一個數字到處一樣，否則就是 bug，要「治本」不要補丁。
4. **主動管理**：事情記下來、主動追、追到有答案為止、完成時把原始需求再顯示一次。
5. **表格化 / 視覺化 / 可自訂**：分類選項自己能增刪改，看圖決策。
6. **對外安靜保守**：廠商群組不外洩金額、不亂插話。
7. **全自動**：排程把資料自己抓進來，人只做判斷。

### 8.2 我的建議（商業化路徑）

**定位建議**：不要賣「又一個 POS / 排班軟體」，而是賣
> **「餐飲老闆的營運整合層 + AI 營運長」**——把你本來分散在 5~6 個系統（POS、訂位、排班、人資、叫貨、宴會）的數字，**自動串成一個老闆看得懂的儀表板 + 一個能用 LINE 問的 AI**。

**為什麼這條路對**：
- 市面上每個單點都有軟體，但**沒人幫老闆把它們縫起來 + 配 AI 問答**。你已經做掉最難的「縫」。
- 你的客戶（餐飲老闆）跟你同類：非技術、要結論、沒空學系統。你最懂他們。

**三階段商業化（由輕到重）**：
| 階段 | 做法 | 收費 | 風險/門檻 |
|---|---|---|---|
| **① 顧問服務先行** | 用你現有 App 當「交付工具」，幫 1~3 家餐飲集團做營運診斷 + 導入 | 顧問費/月費 | 低。驗證願付、累積案例 |
| **② 半客製導入** | 幫客戶接他們的 POS/訂位，給他們一套儀表板 + DD | 導入費 + 月費 | 中。串接工要可複製 |
| **③ 產品化 SaaS** | 多租戶、自助接入、模組訂閱 | 月訂閱 | 高。要改多租戶架構 |

**要先想清楚的幾件事（給 GPT 一起討論）**：
- **護城河**＝那堆逆向串接 + AI 雙邊資料域 + 對話式操作。要能「換一家 POS 也能快速接」才可規模化。
- **技術債**＝目前 `mail-sync.js` 單一巨檔、單租戶。商業化前要評估「多租戶 / 拆服務」的成本。
- **合規與穩定**＝逆向串接會因對方系統改版而斷（已發生過），產品化要有「串接維運」這條線。
- **你是唯一需求來源**＝目前功能都長在「你自己的店」。要找 2~3 家「不同型態」的店壓力測試，避免過度客製化你一家。
- **定價錨點**＝一家店省下的「對帳/報表/排班/催事情」人力時間，換算成月費。
