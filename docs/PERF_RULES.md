# 速度鐵則（張良 2026-10-14 定：「超級重要，一定要做好，每次新功能都要執行，不可以延遲」）

適用：新殼（Next.js＋Supabase）每個頁面、每支 API。GD 舊頁有改到的部分也照做。
這份是規則，不是建議。做不到的要在 PR 寫原因，張良同意才能例外。

## 一、目標數字（每個 PR 都要量，寫進 PR 說明）

| 項目 | 上限 |
|---|---|
| 點分頁到看到內容 | 0.3 秒內先出畫面（先顯示上次的資料，背景再更新） |
| 每支 API 回應（第 95 百分位） | 0.5 秒 |
| 第一次打開 App（手機 4G） | 1.5 秒內可操作 |
| 單頁一次讀進來的資料 | 200 KB 以內；超過就分頁或只拿需要的欄位 |

## 二、必做寫法

1. **換頁不重新整頁**：用 Next.js 前端換頁＋預先載入（prefetch），不要每頁都伺服器現算。
2. **先顯示舊資料、背景更新**（stale-while-revalidate）：讀過的資料存在瀏覽器快取，進頁立刻顯示，再去抓新的。
3. **只抓需要的**：查詢指定欄位、加條件和筆數上限、分頁；禁止「整張表抓回來前端再篩」。
4. **加總在資料庫算**：報表、合計用資料庫的 view／函式算好再回傳，不要把明細全抓回來加。
5. **常查的欄位加索引**（公司、店、日期、狀態）；新表建立時一起建。
6. **不准一筆一筆查**（N+1）：清單要一次查完，不在迴圈裡一筆一筆打資料庫。
7. **伺服器和資料庫放同一區**：Vercel 函式地區要跟 Supabase 專案地區一致（建專案時就對齊）。
8. **只在必要時關快取**：`no-store` 只用在真的每秒都會變的資料（例如金流狀態），要在程式註解寫原因。
9. **大量工作丟背景**：同步外部系統、寄信、算報表走排程或排隊，不卡使用者的畫面。
10. **改資料要立刻有反應**：按下去先更新畫面（樂觀更新），失敗再退回並提示。

## 三、驗收（PR 合併前）

- 預覽站實測三個主要頁面的「點下去到出現內容」時間，貼在 PR 說明。
- 列出這次新增的查詢，標明有沒有用到索引。
- 超過上限的，PR 不合併，先改。

## 四、為什麼

- Belle 財務每個分頁都要等，主因是頁面設定成每次都不快取、伺服器每次現算（回應頭 `no-store`，實測 1.4~3 秒）。
- 換成 Next.js 不會自動變快，快不快看資料怎麼讀。這份就是「怎麼讀」的規則。
