這份是規則，不是建議。做不到的要在 PR 寫原因，張良同意才能例外。

## 一、機房（建專案當下就要對，事後不能改）

- **Supabase 專案選東京（ap-northeast-1）；Vercel 函式地區設東京（hnd1）。**
- Supabase 建立後**不能換地區**；Vercel 新專案預設美東，**一定要手動設定**。
- 理由：台灣最近、兩家都有的機房是東京（實測連線：東京 0.06 秒、首爾 0.09、新加坡 0.10~0.14、美東 0.22~0.24）；LINE 伺服器也在日本。
- 現況對照：GD 和 Belle 的函式都在美東（iad1），台灣打一支幾乎不做事的 API 就要 0.36~0.40 秒。

## 二、目標數字（每個 PR 都要量，寫進 PR 說明）

| 項目 | 上限 |

## 三、必做寫法

1. **換頁不重新整頁**：Next.js 前端換頁＋適度預先載入（prefetch 只做常用的，不全部預載）。
2. **先顯示舊資料、背景更新**（stale-while-revalidate）。
3. **只抓需要的**：指定欄位、條件、筆數上限、分頁；禁止「整張表抓回來前端再篩」。
4. **加總在資料庫算**：報表、合計用 view／函式算好再回傳。
5. **索引**：公司、店、日期、狀態欄位建表時一起建；用查詢計畫（EXPLAIN）確認真的有用到。
6. **不准一筆一筆查**（N+1）。
7. **連線池**：伺服器連資料庫一律走 Supabase 連線池（Supavisor transaction mode）。
8. **權限規則也要快**：公司欄位必加索引，RLS 寫法避免每列重算。
9. **只在必要時關快取**：`no-store` 用在每秒都會變的、個資、權限、財務正確性必須即時的資料，程式註解寫原因。
10. **大量工作丟背景**：同步外部系統、寄信、算報表走排程或排隊；背景工作要能重試且不重複執行。
11. **樂觀更新**：一般操作按下去先更新畫面、失敗退回。**錢、點數、付款、匯款例外**：先顯示「處理中」，伺服器確認才顯示成功。
12. **冷啟動**：常用 API 保持輕量；早上第一個請求的冷啟動不算進第 95 百分位，但要另外記錄。
13. **圖片與字型**：圖片一律 `next/image` 轉 WebP、依尺寸輸出；中文字型用系統字或只內嵌用到的字，禁止整套中文字型。

## 四、快取安全（最容易出事，必守）

- 瀏覽器快取一律按「公司＋使用者」分開存。
- 登出、切換公司時清空快取。店裡共用 iPad 換人一定要清。
- 個人化或公司資料**絕不能**放進 Vercel 公共快取（CDN）。
- 寫入後讓相關快取失效，不能用舊畫面冒充最新資料；斷網時要明顯標示「離線／上次更新時間」。

## 五、怎麼量（每個 PR）

- 工具固定：Vercel Speed Insights（使用者端）＋函式紀錄的執行時間（伺服器端）＋本機腳本對預覽站多次取樣。
- 分「冷／熱快取」各量，取多次樣本，不是點一次就算。
- PR 說明貼：三個主要頁面的換頁時間、新 API 的第 95 百分位、首次下載大小、新查詢是否用到索引。
- 超過上限的 PR 不合併，先改。
- 正式站上線後持續監測，超標自動通知。

## 六、為什麼

- Belle 財務每個分頁都要等：頁面不快取、伺服器在美東每次現算（實測 1.4~3 秒）。真正比例要拆量網路、函式、SQL 才能定案。
- 換成 Next.js 不會自動變快。快不快取決於機房位置和資料怎麼讀，這份就是規則。
