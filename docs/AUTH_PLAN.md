# 帳號權限系統（方案 C：真正安全）實作計畫

> 目標：用 Supabase Auth（帳號＋密碼）取代現在「打一個名字就是身分」的做法。
> 達成：① 無法冒名（沒密碼進不來）② 角色決定能看/能改什麼 ③ 金額/人事等敏感資料在**後端**就鎖住（不是只是前端藏起來）④ 介面永不顯示登入帳號字串。

## 現況（為什麼不安全）
- 登入＝在框裡打一個名字，存進瀏覽器，沒有密碼。任何人打 `goodmask77` 就變管理員。
- 所有資料（含金額）放在 Supabase `pm_documents` 一張表，用 **anon 公鑰**讀寫，**沒有 RLS**（等於公開）。
- 金額全在 `pm_data` 這一筆 JSON 裡 → 只要能讀這筆，就看得到全部金額。

## 角色設計（沿用現有概念）
| 角色 | 能做什麼 |
|---|---|
| admin（張良） | 全部：看金額、改資料、管帳號 |
| manager（工地/財務主管） | 看金額、改進度；不一定能管帳號 |
| staff（基層/工班） | 看工序/工地日誌、回報進度；**看不到金額** |
| viewer（業主/外部） | 唯讀指定頁面；看不到金額 |

## 關鍵：金額要「後端鎖死」→ 需要拆資料
RLS（資料列權限）只能鎖「整列」，不能鎖一筆 JSON 裡的某幾個欄位。
所以要把**金額相關資料**從 `pm_data` 拆到獨立的列/表（例如 `pm_data_finance`），
再用 RLS 規定「只有 admin/manager/finance 角色能讀這列」。
→ staff 即使打開開發者工具，也讀不到金額（後端直接拒絕）。

## 分階段（每階段可獨立上線、不弄壞現在的 App）

### 階段 0：止血（✅ 已完成）
- 今日動態/活動記錄不再顯示登入帳號；登入紀錄只有管理員看得到。

### 階段 1：開 Supabase Auth + profiles 表（多數要你動手）
你要做（我給你逐步畫面指示＋可直接貼的 SQL）：
1. Supabase 後台 → Authentication → Providers → 開啟 **Email**（關閉開放註冊，只有你能建帳號）。
2. Authentication → Users → 手動建立每位夥伴帳號（信箱可用 `名字@ground.local` 這種假信箱＋密碼）。
3. SQL Editor → 貼上我給的建表語法，建立 `profiles`（uid ↔ 顯示名稱/角色/部門/可見頁面）。
我做：提供所有 SQL 與一份「帳號對照表」範本讓你填。

### 階段 2：前端改成真登入
我做：
- 登入框改成「帳號＋密碼」，走 `supabase.auth.signInWithPassword`。
- 身分改由登入 session 決定（拿不到 session＝未登入），**無法冒名**。
- 全程顯示「顯示名稱」，永不顯示帳號/信箱。
- 角色 → 沿用現有 canEdit/isAdmin/頁面權限邏輯接上 profiles.role。

### 階段 3：RLS 上鎖（要你貼 SQL）
我做：提供 RLS 政策 SQL；你貼進 SQL Editor 執行。
- `pm_documents`：未登入不可讀寫；登入者依角色讀寫。
- 一般營運資料：登入即可讀；改寫限 manager 以上。

### 階段 4：金額後端鎖死（資料拆分，較大）
我做：
- 把金額資料搬到受保護的列/表，RLS 限 admin/manager/finance。
- 前端讀不到時自動隱藏金額欄位（staff/viewer 完全看不到）。
- 確保總覽/儀表板/AI 在「無金額權限」下也不會壞。

### 階段 5：在 App 內管理帳號（選配，最方便）
我做：admin 可在 App 內新增/停用夥伴、設角色與頁面權限（透過一個 service-role 的後端函式，金鑰只放後端）。

## 一定要你做的事（無法代勞）
- 在 Supabase 後台開 Email 登入、建立每個人的帳號密碼、貼上我給的 SQL。
- 決定每位夥伴的角色與密碼（我給對照表範本）。

## 風險/注意
- 上 RLS 的瞬間，沒接好的地方會「讀不到資料」→ 我會分階段、每段都先驗證再上正式。
- service-role 金鑰**永遠只在後端**（Vercel 環境變數），絕不進前端/git。
- 一旦改真登入，現在「打名字」的舊方式會停用 → 上線前先把所有人的帳號建好。
