## 1) 漏掉或低估的關鍵風險

- **Vercel serverless 不適合長工與背景任務**：AI 會議、錄音轉檔、push 重試、附件下載都可能超時；若沒有 queue/outbox，會變成「log 有寫、事情沒做完」。

- **`pm_documents` 當 KV 已到風險上限**：通訊、訊息、附件、AI runs 若仍塞 JSON 字串，查詢、去重、權限、稽核都會很痛；個資外洩時也很難追誰看過什麼。

- **Service role 全開權限是大爆炸半徑**：現在後端都用 service role，任何 API bug 都可能讀寫全部資料；做客服訊息與員工私訊後，個資風險會倍增。

- **LINE / Meta 規則依賴太多假設**：reply token 時效、push 計費、官方後台手動回覆是否進 webhook、群組限制、Meta 24 小時例外標籤皆需查證，不能先照規格寫死。

- **錄音在手機 PWA 低估限制**：鎖屏、切背景、來電、中途斷網都可能中斷；若承諾「手機可長錄」但沒替代上傳方案，老闆現場會最有感地失望。

- **AI 個資邊界不是只靠 prompt**：若資料先送進模型再要求不要回答，已經外洩；必須在工具查詢層先過濾，且保留送出給模型的 input snapshot。

- **多官方帳號切 webhook 有營運中斷風險**：三個 LINE 官方帳號目前未盤點，若已有訂位、客服或阿桑系統，直接改 webhook 會漏訊或雙重回覆。

- **通知成本可能失控**：LINE push 依則數與群人數計費，若「收到查詢中」和「答案」都 push，廠商群與內部群會快速燒額度。

## 2) 更好的做法

- **先做「事件表 + outbox」最小關聯式核心，不全系統重構**：只為 conversations/messages/attachments/outbox/ai_runs 建表，其他舊功能繼續用 KV；理由是止住覆蓋與稽核問題，成本遠低於全面 migration。

- **DD 先改成「收事件、存事件、排工作、再回覆」**：webhook 只做驗簽、去重、入庫與快速 ack；AI 查詢與 push 放 queue，理由是最能解決無回應與逾時。

- **第一版收件匣先輪詢，不急做即時聊天室**：手機每 10–30 秒更新列表即可；理由是省掉 realtime 權限、連線、電量與除錯成本。

- **官方 LINE 建議先各自獨立 webhook endpoint 或明確 channel mapping**：不要一開始把簽章驗證寫得太魔法；理由是多帳號故障時較好隔離與回滾。

- **快問先做白名單工具，不急做向量搜尋**：先覆蓋決策帳本、SOP、任務、常見營運數字；理由是來源可控、便宜、也較不會把機密送進模型。

- **AI 會議室先做「半自動文字會議」**：不要先做 LINE Flex 裁決、錄音、三家全流程；理由是先驗證老闆是否真的常用決策帳本，再投入複雜互動。

## 3) 執行順序建議調整

- **把「資料核心 / outbox / 去重 / 權限矩陣」提前到 DD 穩定化內**：否則 DD、收件匣、AI 會議各自補洞，最後會有三套訊息格式。

- **溝通中心外框不要排太前面**：UI 空殼老闆看得到但不能降風險；應在真實訊息能進列表後再做入口，避免假進度。

- **AI 會議室排到 LINE 收件匣穩定之後**：目前最大痛點是漏訊、無回應、對話覆蓋；三家 AI 討論價值高但不是營運止血。

- **廠商移植盤點要現在開始，但切換要最後**：45 群牽涉營運不中斷，應先 mapping、鏡像、抽查，再配合 11 月切換。

## 4) 第一個兩週最值得先做的 3 件事

- **DD 健康頁 + 7 天失敗分類 + 每對話獨立記錄**：老闆會立刻看到「為什麼 DD 沒回」與改善幅度，且直接修掉覆蓋問題。

- **建立最小 `conversations/messages/outbox/inbound_events` 表與去重機制**：先讓 LINE/DD 訊息可靠落地；這是收件匣、人工接手、AI 記憶的地基。

- **三個官方 LINE 與阿桑廠商群盤點表**：列出 webhook、方案、額度、現有系統、是否可改接；理由是這些是外部阻塞，越晚查越容易卡上線。

## 5) 兩份文件矛盾或口徑不一

- **資料模型口徑不同**：A 偏向「每對話一筆 KV / pm_documents 延伸」，B 明確要求完整關聯式 schema；建議採「通訊核心關聯表 + 舊系統暫留 KV」折衷。

- **功能分區不同**：A 把收件匣、AI 助理、會議室、決策帳本放同一「溝通中心」；B 拆成「通訊中心」與「AI 中心」，導航需先定案，否則前端會重工。

- **內部聊天室範圍不同**：A 主要是 DD/App AI 對話進收件匣，B 又加入私訊、工作群組、留言板；這會大幅擴大範圍，建議先排除完整聊天室。

- **開發順序不同**：A 先 DD、外框、快問、收件匣；B 先 P0/P1 共用底層。以現況看，B 的底層要求較安全，但要縮成最小可交付，避免變大工程。

- **AI 會議批次口徑不一**：A 把快問排在會議前，第二部批次又寫會議 A、快問 B；應明確改成「快問先、會議後」，因 DD 立即需要。

### 1. 關鍵風險（文件漏掉或低估）

1. **Vercel Serverless 執行時限與 Webhook 重送風暴（技術風險）**
   - *現象*：Vercel 免費/Pro 版函式執行上限為 10~60 秒。文件 A 規畫在 webhook 內做 AI 工具查詢、多模型推論甚至三家辯論，極易超時中斷。
   - *後果*：超時會導致 LINE/Meta 認定發送失敗並觸發自動重送（Retry），引發重複扣款、重覆推播與訊息轟炸。
2. **LINE Push 訊息計費黑洞（成本風險）**
   - *現象*：官方帳號群組內使用 Push API，是**「按群組內總人數扣額度」**（例如群內 10 人，推 1 則扣 10 則額度），廠商群（45 個）加上內部群，免費額度會瞬間歸零並產生高額帳單。
3. **AI 判斷個資/隱私的不可靠性（法律與營運風險）**
   - *現象*：文件 A 依賴 AI 自動判斷對話是否為「個人薪資/健康/申訴」並標記私人。
   - *後果*：Prompt 漏判率永遠無法歸零。一旦員工的私密病歷或薪資抱怨被漏判給其他主管看到，將面臨勞基法與個資法重大爭議。
4. **手機瀏覽器 Web Audio 錄音限制（技術風險）**
   - *現象*：iOS Safari 與多數 PWA 在螢幕鎖定、來電或切換 App 時，會立即中斷 Web Audio 錄音與分段上傳。
   - *後果*：宣稱能「手機開會錄音 60 分鐘」在真實門店環境極不穩定，易造成主管錄音遺失。
5. **官方帳號「聊天模式」互斥陷阱（平台規則風險，需查證）**
   - *規則*：LINE 官方後台若設定為「聊天（Chat）模式」，在特定版本下 webhook 接收會受限，或無法正常由 API 接管；且手動在後台回覆的內容**不會**觸發 webhook 送回系統（造成對話斷層）。

### 2. 更好的做法（更簡單、更穩、更省錢）

1. **Webhook「收發分離」：引進 Upstash QStash 或純 HTTP 背景解耦**
   - *做法*：`api/inbox-webhook.js` 收到訊息只做「驗簽 + 寫入資料庫 + 轉拋背景佇列 + 立即回傳 HTTP 200」，所有 AI 運算與 Reply/Push 交給背景處理。
   - *理由*：保證不被 LINE/Meta 逾時重送，徹底避開 Vercel 執行超時限制。
2. **LINE 互動堅持「5 秒內以 replyToken 原地回覆」**
   - *做法*：揚棄「先秒回收到，再用 push 送答案」的設計。DD 應採用快取或極簡 Prompt，力求 3~4 秒內直接用 `replyToken` 回覆；真需耗時運算者，一律給 App 連結請使用者回 App 看。
   - *理由*：`replyToken` 完全免費且不扣任何官方帳號則數；Push API 貴且群組計費極高。
3. **敏感資訊隔離改採「物理隔離（專用入口/前綴字）」而非依賴 AI 分類**
   - *做法*：個人隱私（薪酬、請假）強制限定在「DD 私訊」且由特定指令（如輸入 `#私人` 或點選固定選單）啟動，預設直接封鎖其他管理員權限；絕不在公開或工作串中靠 AI 語意判斷過濾。
   - *理由*：規則引擎 100% 穩定零漏判，不耗費額外 token。
4. **真人會議改採「先錄音後整檔上傳」，放棄手機端長時間即時錄音**
   - *做法*：手機先用原生「語音備忘錄」錄完，會後將 m4a/mp3 檔案整檔拖入 App（或直傳 Supabase Storage），再觸發後端轉錄。
   - *理由*：避開 iOS 背景中斷痛點，零開發成本且絕對不掉檔。
5. **放棄即時三家 AI 詰問，改為「單家主答，非同步審查」**
   - *做法*：一般會議由 Claude 產出方案，背後非同步由 GPT/Gemini 提供審查補強，而非同步跑 2 輪多方辯論（9~12 次 API 往返）。
   - *理由*：省下 70% 費用與 80% 等待時間，避免介面卡死。

- **重送被整筆丟掉**：2078 行 `isRedelivery → continue`。重送代表第一次沒收到，跳過＝訊息永久遺失；應改用 `webhookEventId` 去重。
- **「秒回收到→答案 push」會把 DD 日常回答全變計費訊息**：群組 push 按人數計費，10 人群一題 10 則；A 只在收件匣提 push 計費，沒算到項目 1 自己。
- **moneyOK 跟著群組不跟著人**：2727 行薪資/財務是否進 prompt 由 `gid` 決定，`loadSalaryText()` 現在就在餵 AI，與「權限跟著提問者」「AI 讀不到薪資」相反。資料邊界第一步是拆既有餵法，不是新功能。
- **測試環境缺口**：第四部要 PR＋預覽網址驗證，但一個 channel 只能指一個 webhook，「DD 測試群」仍打正式程式。需獨立測試用 OA channel 指向預覽網址。
- **客服帳號切 Bot 模式的營運衝擊**：若店員現在用 OA App 手動回，開 webhook 後手動聊天是否仍可用（需查證）；若不行，「統一從 app 回」是上線第一天的硬需求，要先排訓練。
- **廠商切換當天**：45 群要人手動邀 DD；之後廠商回覆全變 DD 的 push，月額度方案級距要先估（需查證）。
- **快問可能讓 DD 退化**：`council_ask` 定義為只依決策帳本與文件回答，但 DD 的價值在營收/班表/叫貨即時數字；工具查詢沒做完就切路由＝功能倒退。

## 2. 更好的做法
- **先回 200、用 `waitUntil` 背景處理**（`@vercel/functions`）取代「先處理完再回 200」與「秒回＋push」。1:1 私訊另用 LINE loading 動畫 API（免費、不耗 reply token、最長 60 秒；群組是否支援需查證），答案仍走免費 reply，逾時才 push。
- **訊息逐筆 append，不做「一對話一鍵」讀改寫**：同群兩人同時講話仍會互蓋；以 `webhookEventId` 當主鍵自然去重，對話只存狀態與摘要。
- **收件匣用兩張真正的 Supabase 表（conversations、messages，有索引），其餘留 KV**：`data.v` 是 JSON 字串，無法按未讀/狀態排序或搜尋，45 群累積幾個月後 `kvGetPrefix` 整包撈會拖垮列表。決策帳本、會議量小，KV 即可。這是 A、B 的折衷，不必 13 張表。
- **用現成群組「安靜模式」提前鏡像廠商群**：DD 現在就進 45 群、只收不回，歷史從今天累積；11 月切換只需關阿桑機器人＋解除安靜，天然符合 B「鏡像時只有一方發送」。
- **LINE 只留一個 webhook 檔**：依 `destination` 分流到 DD 或客服處理器，驗簽/去重/存檔共用；A 的 `inbox-webhook.js` 會複製第二份邏輯。
- **快問＝同一套查詢工具＋依提問者權限過濾**，文件與決策只是其中一個工具；DD 與 app 共用的是工具層。
- **快問預設 Sonnet＋prompt cache**，Opus 留給會議三席；開放全員後呼叫量是 DD 的數倍。

## 3. 執行順序建議
- **廠商群鏡像提前到第 2 週**：11 月是唯一硬期限、牽涉真金白銀；會議室（8–11）沒有外部期限。
- **會議室延到收件匣批次 2 之後**：決策帳本初期是空的，快問與「自動帶入過去決策」無料可用。
- **項目 7 內部對話放最後**：牽涉公告、信任與自動私人分類誤判，等接手機制穩定再開。
- 項目 3「空殼外框」與第四部「假資料畫面不可標完成」矛盾，建議併入項目 5 交付。

## 4. 前兩週最有感的 3 件事
1. **DD 止血**：強制驗簽（加 strict 開關）、`waitUntil` 先回 200、事件 ID 去重、對話逐筆存、健康頁用現有 log 統計。有感：DD 不再漏回、不再斷在一半。
2. **三個客服帳號「只收不回」進同一頁**：盤點後單一入口依 destination 存檔＋唯讀列表。有感：不用切三個後台就看到客人訊息。
3. **DD 安靜模式進全部廠商群**：同一列表多「廠商」篩選。有感：11 月切換前廠商對話已在 app。

## 5. 兩份文件口徑不一
- **儲存**：A「KV 一對話一筆」vs B「完整關聯 schema＋RLS」→ 見第 2 點折衷。
- **詰問輪數**：A 最多 2 輪 vs B 預設 1 輪可追加。
- **對話狀態**：A 三態 vs B 四態（多「待對方回覆」）；廠商報價需要四態。
- **真人回覆身分**：A「DD 名義＋標（某某回覆）」vs B「員工看到真實人工身分」。
- **範圍**：B 納入內部聊天室、留言板、八工作區導覽改造與產品成本，A 第五部明確排除；B「GD 官方 LINE 保留既有機器人」vs A「廠商機器人全換 DD」。
- **記憶**：A「記決策不記全文」vs B「保存完整原文與輸入快照」，建議統一為「原文保存、檢索只用決策」。
- **私人事項可見者**：A「只有本人與張良」vs B「受限處理群」。
- **多平台底層**：B 要 P1 就建；A 逐批。建議只先保留 `platform/channel_account_id/external_thread_id` 三欄，其餘延後。
