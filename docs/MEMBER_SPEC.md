# GROUN:D 自建會員系統 規格草案 v0.1（2026-10-12）

> **三家審查已完成** → 共識／分歧／第一期建議見 `docs/MEMBER_REVIEW_3AI.md`。等張良裁決分歧 A～F 後，CC 再出 v0.2 正式規格；本文件保留 v0.1 原案供對照。

> 張良 2026-10-12 拍板：**不用 echoss（12cm）**，自己做（B 方案），三家 AI 一起規劃。
> 背景：GROUN:D 官方 LINE 帳號（Messaging API）已接進 App 的「收件匣」；團體訂餐（docs/GROUP_ORDER_SPEC.md）正在做 LIFF 登入，客人在 LINE 內點開連結就拿到 LINE 使用者 ID＋名字。會員系統就從這個 ID 長出來。
> 參考體驗：肯德基點餐機「輸入手機賺 25 點」＋ LINE 推「獲得點數通知」卡片＋「查詢我的點數」。

## 0. 一句話
客人在 LINE 裡點餐／加好友就自動是會員；消費累點、點數換餐或折抵；店家在 GD App（/prep）管名單、規則、核銷；所有通知走 GROUN:D 官方帳號。

## 1. 會員鑰匙與入會
| 項目 | 做法 |
|---|---|
| 會員主鍵 | **LINE 使用者 ID**（GROUN:D 官方帳號 channel 的 userId）。LIFF 的 LINE Login channel 開在同一個 Provider 下，點餐頁、收件匣、推播拿到的 ID 一致 |
| 入會點 | ① 團體訂餐頁 LIFF 登入（自動）② 官方帳號加好友（follow 事件自動建殼）③ 現場：店員在 /prep 用手機號碼找／建 ④ 之後：會員卡 LIFF 頁自己填手機 |
| 手機號碼 | 選填，但要領點數／兌換要有（防重複、現場對人用）；一個手機只能綁一個 LINE ID，衝突由店家處理 |
| 同意 | 入會第一次跳同意文字（個資蒐集目的：點數、通知、訂單）；可退會（標記，不刪流水） |

## 2. 資料（新增，照 App 現有 KV＝Supabase pm_documents 慣例；是否改真表見 §9 問題 1）
| 鍵 | 內容 |
|---|---|
| `pm_member_<uid>` | {uid, name, pic, phone, email?, company?, taxId?, joinedAt, src(order/follow/staff/card), tags[], tier, balance(快取), earned, redeemed, lastVisitAt, lastOrderAt, consentAt, status(active/left/blocked), note(店家內部), edits[]} |
| `pm_member_idx` | 列表索引 [{uid,name,phone(遮罩),tier,balance,lastVisitAt}]（≤ 數千筆；超過見 §9） |
| `pm_member_phone` | {phone→uid} 反查 |
| `pm_mpts_<uid>_<ts36><rand>` | 點數流水一筆一檔（只插入不改）：{uid, t, kind(earn/redeem/adjust/expire), pts, amount(消費額), ref(orderId/posRef/rewardId), by(系統/店員), note} |
| `pm_member_cfg` | 規則：賺點（每消費 N 元 1 點、四捨五入規則、哪些通路算：團體訂餐／現場／外送不算）、點數有效期（月）、等級門檻（年消費額）、獎勵清單 [{id,name,pts,type(折抵金額/換餐點 itemId),stock,active}]、歡迎訊息、推播開關 |
| `pm_mredeem_<id>` | 兌換單：{id, uid, rewardId, pts, code(6 碼核銷碼), status(pending/used/void), createdAt, usedAt, usedBy} |

餘額＝流水加總；`balance` 只是快取，每次寫流水後重算（同一支算法，別兩邊各算）。

## 3. 賺點
| 來源 | 怎麼進 |
|---|---|
| 團體訂餐 | 單子標「完成」時：每個 LINE 身分的人依自己小計賺點；手打名字（匿名）不賺；共用品項歸主辦人（建單對話的客人） |
| 現場消費（喬亞 POS） | 第一期人工：店員在 /prep「會員」頁掃客人會員卡 QR（或輸手機）→ 輸入消費金額 → 入點。第二期：對 POS 日結逐筆比對（POS 有單號／時間）做抽查 |
| 外送平台 | 不賺（規則可開） |
| 店家手動 | 加點／扣點／補登，要寫原因，留誰操作 |
| 活動 | 加好友送 N 點、生日點、推薦碼（第二期） |

## 4. 用點
- 會員卡頁選獎勵 → 產生 6 碼核銷碼＋QR（10 分鐘有效）→ 店員在 /prep 輸碼或掃碼核銷 → 扣點、寫流水、客人 LINE 收「已兌換」。
- 折抵型：核銷時店員在 POS 手動打折（第一期不串 POS）。
- 團體訂餐可直接用點折抵（鎖單前主辦人選，扣主辦人的點）。

## 5. 客人看到的（LIFF 頁 `/member`）
- 會員卡：名字、等級、點數、QR（含 uid 簽章，店員掃）
- 點數紀錄（流水）、可兌換清單、我的兌換碼
- 個人資料：手機（必填才能兌換）、公司／統編（團訂開發票用）
- 官方帳號 Rich Menu 加「會員卡」「團體訂餐」兩顆

## 6. 店家看到的（/prep「會員」分頁，權限 member）
- 名單：搜尋（姓名／手機末 4 碼／LINE 名）、篩選（等級／標籤／最近沒來）、每人卡：資料、流水、兌換、訂單（接團體訂餐＋收件匣對話）
- 給點／扣點／核銷（輸碼或 iPad 相機掃 QR）
- 設定：賺點規則、等級、獎勵清單（可增刪改排序、庫存）、同意文字、歡迎訊息；全部視覺化可勾選
- 數據：新會員／活躍／回訪、點數負債（未用點數×折抵價值）、兌換率
- 個資守門：手機完整號碼只有審核人／主管看得到（沿用 secretOK），其他人看遮罩

## 7. 通知（通知鐵則：兩端都發）
| 事件 | 客人（LINE 官方帳號） | 店家 |
|---|---|---|
| 入會 | 歡迎＋目前點數＋會員卡連結 | — |
| 賺點 | 卡片：+N 點、原因、金額、「查詢我的點數」 | — |
| 兌換建立／核銷 | 核銷碼／已兌換 | 鈴鐺（核銷人） |
| 點數即將到期 | 到期前 30 天提醒（可關） | — |
| 推播（行銷） | 分眾（標籤／等級／久沒來）走行銷大師，按人數計費要顯示預估額度 | — |
LINE push 按人頭扣額度（200 則免費方案會不夠）→ 賺點卡片能用 reply 就 reply；行銷推播要先看額度。

## 8. 與現有系統的接法
- 收件匣：對話的 uid＝會員 uid → 對話表頭顯示會員等級／點數／最近訂單；可直接「給點」
- 團體訂餐：鎖單→完成時入點；客人頁登入後顯示「你有 N 點」
- DD：`query_member`（主管／審核人限定，個資遮罩）
- 積分中樞（夥伴用 pm_points）**不混用**：客人點數是另一套帳

## 9. 要三家 AI 回答的問題
1. 儲存：會員與點數流水用現有 KV（pm_documents 一筆一檔＋索引檔）夠不夠？名單到幾千人、流水到幾十萬筆時要不要改成真正的 Supabase 表？建議的切換時機與最省力的做法。
2. 點數正確性：流水＋餘額快取的設計有沒有漏洞（同時寫入、重複入點、退款回收點數、作廢訂單）？要哪些冪等鍵？
3. 防弊：匿名（手打名字）不給點、LIFF access token 伺服器驗、核銷碼 10 分鐘、店員手動給點留痕——還缺什麼？
4. 主鍵：LINE userId 當主鍵、手機當輔助，風險（換手機／封鎖解除／換 LINE 帳號）怎麼處理？
5. 現場 POS（喬亞）沒 API 下，第一期「店員掃 QR＋手輸金額」是否可行？有沒有更省人力又不易作假的做法？
6. 個資法／同意：最少要哪些文字與功能（查詢、更正、退會、刪除）？
7. 第一期範圍建議（最小可上線）與分期；哪些是過度設計。
8. LINE 方案成本：push 計費下，哪些通知該砍／改 reply／改 LIFF 內顯示。
