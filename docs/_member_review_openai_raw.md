## §9：依序回答 8 題

### 1. 儲存：KV 夠不夠？何時改表？

**結論：會員與點數從第一天就用真正的 Supabase 表，不等到幾千人才搬。**

- 問題不只是資料量，而是：
  - 手機唯一性、重複入點，需要資料庫唯一約束。
  - 扣點、核銷、庫存，需要同一交易完成。
  - 共用 `pm_member_idx`／手機索引檔容易互相覆蓋，產生「會員存在但搜尋不到」。
  - 每次入點重掃全部流水，成本會隨歷史資料增加。
- **最省力做法：不改整套 App，只把會員帳務核心改表。**
  - `members`：內部會員 ID、狀態、必要個資。
  - `member_identities`：LINE 身分與會員的對應。
  - `point_accounts`：品牌錢包、可用／保留點數。
  - `point_ledger`：不可任意修改的點數流水。
  - `redemptions`：兌換狀態。
  - `notification_outbox`：待發通知與重試狀態。
  - 有效期若要上線，再加點數批次及扣抵分配紀錄。
- 名單直接查表、分頁、建索引，不另維護全員索引 JSON。
- 設定、頁面文案可暫留 KV；**設定異動要有版本，交易記下使用的規則版本。**
- 用 Postgres function／Supabase RPC 執行原子交易；不是 Node 連續呼叫三次資料庫就算交易。
- 若已有試用資料：停寫 → 匯入 → 核對逐人餘額 → 切換。避免長期雙寫。

### 2. 點數正確性與冪等鍵

**結論：流水＋餘額快取方向正確，但「先寫流水、再重算餘額」不是安全交易。**

- 每次異動在同一資料庫交易內：
  1. 驗證來源、權限及冪等鍵。
  2. 鎖定會員點數帳戶。
  3. 檢查可用餘額、兌換及庫存。
  4. 寫流水，更新帳戶餘額及兌換狀態。
  5. 寫通知 outbox，提交交易。
- 平常用原子增減更新餘額；定期用流水加總對帳。**流水是依據，餘額是交易中同步維護的結果。**
- 建議的冪等鍵，必須有資料庫 `UNIQUE` 約束：

| 情境 | 建議鍵 |
|---|---|
| 團訂入點 | 品牌＋訂單 ID＋固定結算項目／會員分配 ID |
| 現場入點 | 品牌＋門市＋營業日＋POS 單號 |
| 手動調整 | 一次操作的 request ID；重試沿用同一 ID |
| 兌換建立 | 會員＋一次操作的 request ID |
| 兌換扣點 | redemption ID |
| 退款回收 | refund ID＋原入點項目 ID |
| 到期扣除 | 點數批次 ID＋到期事件 |
| LINE webhook | webhookEventId，用於事件去重 |

- 訂單來回切換 `done`，不能再送一次點數；不能用「目前時間」作入點冪等鍵。
- **團訂必須「完成且符合收款條件」才入點**，不只看店員按完成。
- 退款應新增反向流水，連結原交易；部分退款依原結算規則重算應回收差額，不修改原流水。
- 點數已花掉才退款，要明訂政策：允許帳戶成為欠點狀態、暫停兌換、後續入點抵欠點等；不可直接歸零掩蓋差額。
- 團訂還在 KV：採「可重跑結算工作＋每日找漏單」，即使訂單狀態成功、會員入點失敗，也能補回。
- 若有有效期，必須按批次記錄剩餘點數、到期日，兌換優先用最早到期批次；單純加總流水不足以正確到期。

### 3. 防弊還缺什麼？

**結論：目前只有基本留痕，還缺身分所有權、核銷防猜、員工權限及交易來源驗證。**

- **LINE 身分只能由後端驗證結果取得。**
  - 驗 access token 的有效性及對應 channel，再向 LINE 取得身分；或後端驗證 ID token 的簽章、有效期、受眾等。
  - 不接受前端自行送来的 `uid`、姓名或解碼後 token 當證據。
  - token 不放網址、不進一般日誌。
- 團訂的每列要有不可由客人任意更改的 `owner_member_id`。
  - 主辦人代填姓名不代表對方已登入。
  - 同一人有多列，先合併其消費額再依規則算點。
  - 折扣、共用品項、服務費、點數折抵的分攤，全部由後端算。
- **6 碼碼只能是查找入口，不能是完整授權。**
  - 安全亂數、有效期間內不重複、店家登入後才能查。
  - 限速、錯誤次數限制、過期由伺服器時間判斷。
  - 核銷時再次查餘額，原子地完成扣點與狀態更新。
- 第一期間建議「建立碼不保留點數，核銷才扣」：
  - 畫面明示尚未兌換成功。
  - 多碼同時使用仍只能扣出可用餘額。
  - 不先保證庫存；若要保證，就得連點數與庫存一起保留、到期一起釋放。
- 會員卡 QR 用短效、用途限定的不透明 token；**簽章不會隱藏 uid，也不能阻止截圖轉傳。**
- 給點、扣點、核銷、改規則、看完整手機、匯出名單分權；高額手動調整需主管核准。
- LINE webhook 驗簽；Supabase 開 RLS，service role key 絕不進前端；所有後端端點仍須自行檢查權限。
- 加異常告警：同店員大量補點、同 POS 單號反覆申請、單人短時間多筆高額入點。

### 4. LINE userId 當主鍵、手機當輔助

**結論：用內部 UUID 當會員主鍵，LINE userId 當登入身分；手機不是會員所有權證明。**

- 同 Provider 下，LINE Login 與 Messaging API 身分可對應；部署前用實際帳號驗證，並把 Provider／channel 設定列入上線檢查。
- `member_identities` 保存 Provider、LINE userId、member ID；**顯示名、照片不能拿來比對會員。**
- 單純換手機裝置或門號、但沿用同一 LINE 帳號，通常不需要搬會員。
- 封鎖／解除封鎖不是退會／重新入會；`unfollow` 不應清除點數。
- 換 LINE 帳號才需要受控移轉：
  - 優先由舊帳號驗證、新帳號確認。
  - 舊帳號無法登入時走人工審核及等待期。
  - 有完整移轉紀錄，舊身分停用；不能只憑姓名或手機直接搬點。
- 手機若用於登入、綁定或找回，至少需 OTP 驗證；即使有 OTP，也不能只憑新門號持有人就繼承舊會員，因為門號可能回收。
- **不建議「一支手機只能一個會員」硬限制**：家庭共用、公司電話、門號回收會誤傷。
- 店員只有手機時，先建待認領顧客資料或待補點紀錄，不要製造假的 LINE uid。
- GROUN:D、A Beach 第一階段分開錢包、分開规则；共用身分不等於共用點數。

### 5. POS 沒 API，掃 QR＋手輸金額可行嗎？

**結論：可以作第一期，但必須再輸 POS 單號；只有掃 QR＋金額不足以防重複與作假。**

- 最少留下：門市、營業日、POS 單號、符合累點的金額、會員、操作員、時間。
- 客人卡只負責辨識會員；**金額與收款事實以 POS 收據為準**。
- 流程做成一頁：掃卡 → 輸單號／金額 → 顯示會員遮罩資訊 → 確認；不必每筆拍收據，減少個資與操作負擔。
- 先確認喬亞現有能力：日結明細匯出、CSV、收據條碼、固定單號格式，未必一定要 API。
- 若有匯出：
  - 每日自動對帳已入點單號。
  - 找不存在、金額不符、退款／作廢、重複筆數。
- 若完全沒有可機讀明細，人工入點無法真正證明交易存在，只能靠抽查、限額與主管覆核降低風險。
- 更省人力的候選方案是「客人填收據單號、後台對帳後補點」，但不適合急著立即兌換，也不能只憑單號立即發點。
- 不建議第一期上 OCR：它能少打字，不能取代交易驗證，且會新增辨識錯誤。

### 6. 個資法／同意

**結論：加好友不是同意入會；要把會員條款、個資告知、行銷選擇與退會處理分開。**

- `follow` 先建通訊聯絡紀錄即可；客人進 LIFF 閱讀告知、接受會員條款後才成為會員。
- 最少個資告知內容：
  - 蒐集者的法律實體及聯絡方式，不只品牌名。
  - 蒐集目的、資料類別。
  - 利用期間、地區、對象及方式，包括實際雲端／服務供應商安排。
  - 查詢、閱覽、複製、更正、停止蒐集／處理／利用、刪除等權利及申請方式。
  - 可否不提供資料，以及不提供的影響。
- 會員條款另外写清楚：累點基準、退款回收、有效期、兌換限制、退會後点數處置及規則變更方式。
- 記錄接受的條款版本、個資告知版本、時間、會員；只存 `consentAt` 不夠。
- 行銷要有獨立選擇與方便拒絕方式；首次行銷提供拒絕方式，拒絕後停止。不能因拒收行銷就不讓人兌換。
- 不應無理由要求領點／兌換一定填手機；LINE 身分已足以運作。手機、生日、email 都要能說明必要性。
- 提供：
  - LIFF 查詢與更正。
  - 退會及權利申請入口。
  - 後台受理、身份核驗、處理紀錄及依適用期限回覆的流程。
- **退會不等於永久留著所有個資。**
  - 必須有保存期限、刪除／匿名化排程、備份輪替政策。
  - 依法或為履行法定義務須保留的交易資料，限定範圍、用途與存取權。
  - LINE ID 本身也屬可識別資料，不能只刪姓名電話就宣稱匿名化。
- 統編／公司資料優先留在訂單開票用途，不必複製到永久會員檔。
- 上線文字請台灣法律專業人士按實際營業主體、資料流及最新法規確認。

### 7. 第一期最小範圍與分期

**結論：第一期要有完整但簡單的賺點—兌換閉環，把等級、分眾與團訂折抵延後。**

- 第一期：
  - 單品牌、單一累點規則。
  - LIFF 入會、會員卡、流水查詢。
  - 團訂完成且符合收款條件入點。
  - 現場憑 POS 單號人工入點，可先限少數店員試營運。
  - 一項固定點數獎勵、店員原子核銷。
  - 退款、補點、權限、對帳、基本個資功能。
- 不開放第一期自訂複雜規則；少量設定即可，避免老闆誤改造成負債。
- **有效期只能二選一：**
  - 第一期明確無到期，並控制發點量；或
  - 第一日起就做批次與到期機制。
  - 不可先承諾一年到期，卻等第二期才實作。
- 第二期：POS 匯入對帳、較多獎勵、庫存、到期提醒、收件匣資訊。
- 第三期：等級、分眾、推薦、團訂點數折抵及金流。
- 金流綁定不是會員第一期的前置需求。

### 8. LINE 方案成本與通知

**結論：取消「每個會員事件都 LINE 通知」；預設 LIFF 顯示，必要事件才 push，reply 只用在真正有 webhook 的時機。**

- LIFF 登入、點兌換、店員給點，**不會因此取得可用的 reply token**。
- reply token 來自 webhook、只能用一次且有有效限制；不是可延後使用的免費推播額度。不要把「50 秒內」當成普遍保證。
- 建議：

| 事件 | 第一期做法 |
|---|---|
| 加好友 | 可用當次 reply 發入會入口，不宣稱已成會員 |
| LIFF 入會完成 | 頁面顯示，不另 push |
| 賺點 | 頁面／流水顯示；首筆或重要補點再選擇通知 |
| 建立兌換碼 | LIFF 顯示，不 push |
| 核銷完成 | LIFF 顯示；需要收據式通知才 push |
| 到期提醒 | 有到期制度再做，按人彙總，不按批次連發 |
| 行銷 | 獨立同意／拒收管理，預覽人數、額度及發送上限 |

- 客人查點可從 Rich Menu 開 LIFF；若傳訊詢問，可用該事件 reply 回覆。
- 官方帳號的可達性要另外處理：LIFF 登入不保證已加好友，封鎖者也不能可靠推送。
- 計費不能理解成「單月去重後的人頭數」：同一人多次收到計費訊息，仍會累計；同一 API 請求內多個訊息物件的算法也應依官方說明處理。
- 免費額度、方案價格及加購上限，上線前查台灣官方最新方案；不要硬編碼「200」。
- outbox 負責重試、去重及失敗告警；**通知失敗不回滾已成功的點數交易**。重試支援使用 LINE retry key，並記錄發送結果。
- 店家核銷成功直接在操作畫面確認，不必每筆再送一個鈴鐺。

## B. 漏掉的風險

- **團訂分享連結不是會員所有權。**原規格「連結即授權、大家用同一碼」不能直接支援安全的「每人只能改自己的列」；要分離主辦人權限、個人列權限與分享權限。
- **公開計價圖洩漏資料。**姓名、電話、統編及消費明細不宜直接丟永久公開圖庫；使用受控存取或有限期連結，LINE 圖片傳送限制也要實測。
- **前端共用計價算法不等於可信。**後端必須重算並保存結算快照，不能接受客人送来的小計作入點依據。
- **折扣與四捨五入未定義。**個人分攤總額須等於全單符合累點金額；避免拆多列、多次取整多送點。
- **POS 手動折扣與會員扣點無法跨系統原子化。**若扣點成功、POS 沒折扣，需要受控補償流程；若先折扣後核銷失敗，也要有人處理。第一期用換固定品項比金額折抵容易控管。
- **獎勵規則改動會影響既有兌換。**兌換建立時保存名稱、所需點數及規則快照；不能事後改價造成爭議。
- **serverless 工作可能中斷。**不用程序記憶體鎖、`setTimeout` 或回應後背景工作當可靠任務；使用資料庫工作紀錄、Cron／持久化佇列。
- **內部與 AI 洩漏。**遮罩必須在後端完成；完整電話、token、會員備註不進 DD／LLM 提示、一般日誌及前端下載資料。
- **點數負債只是管理估算。**換餐不一定有固定折抵價值；管理報表與正式會計認列要分開，請會計師確認。
- **備份與事故處理未規劃。**需要還原演練、日對帳告警、操作稽核、權限撤銷及個資事件處理流程。

## C. 第一期最小範圍：我的版本

**先只上 GROUN:D，限定店員與客群試營運，再擴大。**

### 必做

1. **入會與身分**
   - LIFF 後端驗證。
   - 內部 member ID。
   - 個資告知、會員條款版本。
   - 手機非必填；follow 只建立聯絡紀錄。

2. **帳務**
   - 真正表、原子交易、唯一冪等鍵。
   - 一套固定累點規則。
   - 團訂結算入點、POS 單號人工入點。
   - 退款回收、主管調整、每日對帳。
   - 第一期明確無到期；若商業上不能接受，先實作批次到期再上線。

3. **客人頁**
   - 點數、流水、短效會員 QR。
   - 一項獎勵、短效兌換碼。
   - 退會與個資權利申請入口。

4. **店員頁**
   - 名單搜尋、掃卡、入點、核銷。
   - 權限分離、操作稽核。
   - 必要設定，不做通用規則編輯器。

5. **通知**
   - LIFF 顯示為主。
   - LINE 入會入口可 reply。
   - 少量必要 push，有 outbox 與費用上限。

### 暫不做

- 等級、生日、推薦、標籤行銷。
- 多品牌點數互通。
- 團訂點數折抵、金流綁定。
- OCR、大型儀表板、完整視覺化規則引擎。

### 上線驗收門檻

- 同一訂單重送十次，只入點一次。
- 同一餘額同時核銷兩次，不會超扣。
- 入點已成功但 API 回應中斷，重試不重複。
- 退款、作廢及點數已花掉的退款，都有明確結果。
- 過期核銷碼拒絕；匿名者不能冒領他人的訂單列。
- LINE 發送失敗不影響點數，且不會無限重送。
- 每位會員的帳戶餘額與流水可核對，差異能告警。
- 退會、帳號移轉、權限撤銷及資料還原，至少演練一次。

**優先順序：帳務正確 → 身分與權限 → 最小兌換閉環 → 通知與行銷。**
