### 財務：資料流與單一事實來源
來源（POS✅／叫貨單✅／出勤✅／分潤✅／EM✅／🔴網銀 CSV／🔴廠商月結單／🔴飯店月結單／🔴貸款合約／🔴薪資設定／🔴電子發票）→ 子帳（🔴 bank_txn、ap_invoice、payroll_run、loan_schedule、hotel_recon、tax_doc）→ 總帳 ledger（沿用內帳藍圖，加 ref／bank_txn_id／科目／門店／稅別／關帳）→ 產出（餘額、未對帳、應付帳齡、損益、現金流、401 底稿）。

- 定位＝管理帳（單式 ledger＋子帳），不是雙分錄會計；401 只出給記帳士的底稿。

## 2. 財務中心架構

### 核心原則

| 原則 | 說明 |
|---|---|
| 一切財務資料要有「來源單據」 | 銀行明細、廠商月帳、薪資表、POS 日結、401 發票都要保留原始來源 |
| 銀行明細不是損益來源 | 銀行只是付款／收款證據，不代表費用或收入歸屬月份 |
| 廠商月帳與應付帳款不能各算各的 | **廠商月帳應升級為應付帳款的來源單據** |
| ledger 不應手填為主 | 交易明細應由 POS、應付、薪資、銀行、稅務等模組過帳產生 |
| 老闆看表格與圖，財務看明細 | 同一份資料，分成總覽、明細、異常三層 |

---

### 是否沿用既有 accounts / ledger 概念？

**可以沿用，但要升級。**

| 舊概念 | 建議處理 | 說明 |
|---|---|---|
| accounts | 沿用並擴充 | 原本 bank／company／cash／petty／loan 概念是對的，可作為「帳戶與科目」基礎 |
| ledger | 沿用但升級 | 原本 expense／transfer／income 太簡化，未來要支援應付、薪資、貸款、稅務、轉帳、調整 |
| petty cash | 沿用 | 零用金仍然需要，且可連收據照片 |
| loan account | 沿用但拆細 | 不只是一個帳戶，要有貸款合約、期數、本金、利息、餘額 |
| 單式流水帳 | 不建議繼續擴大 | 若要產出損益表、資產負債表、現金流，最終要接近雙分錄邏輯 |

### 建議資料層級

| 層級 | 表格／模組 | 說明 |
|---|---|---|
| 來源層 | POS 日結、叫貨單、廠商月帳、薪資表、銀行 CSV、貸款合約、發票 | 原始資料，不直接改寫 |
| 業務單據層 | sales_daily、ap_bills、payroll_runs、loan_schedules、tax_invoices | 整理後可被財務使用的單據 |
| 過帳層 | ledger_entries、ledger_lines | 財務交易明細，產出報表 |

#### A. 廠商月帳 vs 應付帳款

| 項目 | 建議 |
|---|---|

## 4. 風險／反對意見

### A. 權限風險

| 風險 | 說明 | 建議 |
|---|---|---|
| 財務資料外洩 | 銀行、薪資、貸款、稅務不應讓一般夥伴看到 | 財務中心預設只給老闆、財務、指定主管 |
| 薪資敏感 | 店長可能只該看部門總額，不該看個人薪資 | 薪資頁面要分「總覽權限」與「個人明細權限」 |
| 分頁合併後權限變複雜 | 原本單一入口變中心＋子分頁 | 權限要到子分頁層級，不只中心層級 |
| 通知誤發 | 財務待辦或薪資提醒可能發錯對象 | 通知中心也要吃權限設定 |

---

### B. 資料一致風險

| 風險 | 說明 | 建議 |
|---|---|---|
| 廠商月帳與 AP 重複計算 | 成本總覽算一套，財務應付算一套，最後對不起來 | 指定 ap_bills 為單一事實來源 |
| 銀行支出被誤認為費用 | 付款日不等於費用發生日 | 報表要分「權責發生」與「現金流」 |
| POS 營收與銀行入帳不同步 | 信用卡、平台、飯店結算會延遲入帳 | 建立收款對帳，不用銀行直接當營收 |
| 薪資來源混亂 | NUEiP、分潤、自建打卡、人工 Excel 都可能不同 | 每月建立 payroll_run，確認後鎖定 |
| 稅務資料不完整 | 沒有發票資料，只靠支出推 401 會錯 | tax_invoices 要獨立建表 |

---

### C. 改動範圍風險

| 風險 | 說明 | 建議 |
|---|---|---|
| 一次改太多，現場找不到功能 | 31 個入口突然重整，PT 會不習慣 | 第一階段先保留搜尋與舊入口別名 |
| 成本模組剛上線又改位置 | 使用者可能以為功能不見 | 用「原物料／成本」中心承接，保留徽章 |
| 財務系統牽涉會計邏輯 | 若一開始就做完整會計系統會太重 | 先做「管理財務」，再逐步靠近正式會計 |
| 多資料源同步不穩 | POS、GOPS、boss-api、NUEiP、銀行匯入都有失敗可能 | 新增「資料同步狀態」頁面 |

---

### D. 夥伴習慣風險

| 風險 | 說明 | 建議 |
|---|---|---|
| 舊名稱與新名稱認知不同 | 例如採購、叫貨、物料庫關係不清 | 中心內保留舊名稱副標，例如「叫貨／採購」 |
| 手機操作層級變深 | 合併後可能要多點一次 | 今日工作放高頻快捷，並加搜尋 |
| 老闆可改分頁名稱導致文件失效 | 名稱被改後教學文件與工程溝通會亂 | 系統內部用固定 key，顯示名稱可改 |
| 徽章數字位置改變 | 438 待處理如果藏太深，會被忽略 | 中心層級也顯示徽章，例如「物料與成本 438」 |

#### (3) 單一事實來源（SSOT）的解決方案
* **痛點**：目前成本模組有「廠商月帳（自填）」，未來又有「應付帳款」，兩套帳必打架。
* **解法**：
  * **叫貨與驗收**（GOPS / boss-api）是「**業務事實**」（進了多少貨）。
  * **應付帳款模組 (`fin_ap_invoices`)** 是「**財務唯一事實**」：將現有的「廠商月帳」升級，業務端確認驗收數量後，資料自動進入財務應付待審核池；財務審核發票、折讓、扣款後「封帳」，產生最終應付金額。成本總覽只讀取封帳後的應付金額，禁止現場人員另開表單記帳。

#### (4) 沿用舊主 App `accounts` / `ledger` 概念評估
* **評估結果：完全合適，必須沿用並升級。**
* **理由**：
  * 老闆是財務出身，熟悉借貸平衡與帳戶概念。
  * `accounts` 延伸為：銀行帳戶 (bank)、公司主帳 (company)、各店零用金 (petty)、貸款負債 (loan)、虛擬結算戶 (hotel)。
  * `ledger`（明細分類帳）為流水核心，每筆交易（expense 支、transfer 調撥、income 收）都必須帶有 `account_id`、關聯憑證（發票號）、關聯模組（廠商 AP 或薪資單），這樣未來產出「損益表」與「現金流量表」不用重新架構。

### 4. 風險與反對意見（防坑指南）

1. **權限穿透風險（最危險）**
   * *問題*：合併在同一個 `/prep` App，如果 API 層（Backend）沒有嚴格依身份（Role/Token）做 Row-Level 與 Column-Level 隔離，PT 工讀生只要抓封包或手機畫面被瞄到，就能看到其他夥伴薪資、合約抽成與營收利潤。
   * *解法*：前端路由隱藏**不足以**防弊，財務中心的所有 API 必須在伺服器端做嚴格權限檢驗（僅限 Owner / Finance 角色）。
2. **網銀未開 Open API 導致的人工匯入怠惰**
   * *問題*：中小型銀行通常沒有低成本的 Open API 自動抓明細，若仰賴財務每天上傳 CSV，一旦漏傳 3 天，現金流預測全毀。
   * *解法*：初期不要追求「即時」，設計「每週對帳流程」，搭配上傳防呆驗證（若餘額與上期期末不合即報錯）。
3. **前線現場人員的認知摩擦（改動習慣反彈）**
   * *問題*：側欄 31 項一口氣收成 8 項，前線夥伴短期內會抱怨「找不到盤點在哪」、「叫貨被收去哪裡」。
   * *解法*：切換初期在新分頁頂部提供「全域搜尋（Search Palette）」；並將前線每天必用的（班表、打卡、叫貨）固定在「夥伴工作站」與「物料庫存」的前兩頁。
4. **廠商月帳過渡期「雙軌混亂」**
   * *問題*：現在店長習慣在「成本總覽→廠商月帳」自己填寫數字，一旦財務系統上線應付帳款，會出現「店長填一套、財務算一套」。
   * *解法*：直接將舊「廠商月帳」改為唯讀，或轉化為「叫貨對帳狀態」，輸入權限收歸財務，避免資料不一致。

## 2. 財務中心架構

### 2.1 一句話定位
**成本模組管「用掉了多少」（權責），財務中心管「錢實際進出、欠誰、誰欠我」（現金＋應付應收），兩邊靠「叫貨單」「薪資單」「POS 日結」三條線接起來，不各算各的。**

### 2.2 六大功能 × 資料來源 × 自動程度

| 功能 | 資料從哪來 | 自動／人工 | 進哪張表 | 產出 |
|---|---|---|---|---|
| **銀行明細** | ① 網銀匯出 CSV／Excel 上傳 ② Gmail 轉帳通知（FINANCE_MODULE 路線圖已列）③ 未來銀行 API | ① 人工每週上傳（主來源）② 半自動（AI 解析→待確認）③ 🔴 目前台灣中小企業拿不到 | `bank_txn`（原始、不可改、含 bank_ref 去重） | 各帳戶餘額、未對帳清單、現金日報 |
| **貸款** | 貸款合約（本金、利率、期數、每月還款日）、銀行扣款通知 | 合約手填一次；每期還款由 `bank_txn` 自動配對 | `loan`（主檔）＋`loan_schedule`（系統展開每期本金／利息） | 剩餘本金、下期還款日、年度利息（進損益） |
| **廠商貨款（應付）** | GD：GOPS 叫貨單＋明細（已自動）；AB：boss-api 叫貨單＋明細（已自動）；廠商月結單／發票 | 進貨明細自動；**月結單金額人工上傳或手填**；付款由 `bank_txn` 配對 | `ap_invoice`（一張廠商月結單／發票一列，連回叫貨單 ids） | 應付帳齡、本月該付清單、叫貨 vs 月結 差異 |
| **薪資** | NUEiP 出勤＋班表（已自動）、自建打卡、分潤試算（已自動）；底薪／時薪／勞健保級距／扣款 | 工時自動；薪資設定手填；每月「跑薪資」一鍵產生 | `payroll_run`（月）＋`payslip`（每人） | 薪資單（個人私有）、薪資總表、勞健保／二代健保／勞退應付 |
| **飯店對帳** | POS 付款別裡的「房帳／簽帳／飯店代收」（Eats365 已有付款別欄）；飯店月結單 | POS 端自動；**飯店月結單人工上傳**；入帳由 `bank_txn` 配對 | `hotel_recon`（月：我方 POS 金額 vs 飯店金額 vs 實收，含抽成／租金若有） | 飯店應收餘額、差異明細 |
| **401 申報** | 銷項：喬亞／Eats365 開立的電子發票（匯出檔或財政部平台下載）；進項：`ap_invoice` 的發票號／稅額 | 銷項半自動（每雙月匯出一次）；進項靠 AP 鍵入（可拍照 AI 讀發票） | `tax_period`（雙月）＋`tax_doc`（每張發票） | 401 工作底稿（給記帳士）、應納／留抵稅額、未取得發票的進貨警示 |

> 飯店對帳的假設：A Beach 在飯店內，客人可掛房帳由飯店月結給餐廳。若實際是「飯店收租／抽成」，則對帳方向相反（我方應付），表結構一樣，只是正負號。**請張良確認是哪一種或兩種都有。**

### 2.4 單一事實來源（SSOT）表——最重要的一張

| 問題 | 唯一答案在哪 | 其他地方只能「引用」，不能另算 |
|---|---|---|
| 這家店今天賣多少 | POS 日結（`pm_pos_*` / `pm_ab_*`，已有） | 財務、損益、飯店對帳都引用它，不再手填營收 |
| 本月跟 X 廠商**進貨**多少 | 叫貨單明細（GOPS／boss-api，已有） | 成本總覽的「廠商月成本」用這個 |
| 本月**欠** X 廠商多少 | `ap_invoice` | 成本總覽「廠商與月帳（自填）」要改成 **AP 的視圖**，不再另外存一個自填數字 |
| 本月**付了** X 廠商多少 | `ledger`（expense, ref=ap_invoice） | 應付餘額＝ap_invoice − ledger 已付，系統算，不手填 |
| 帳戶現在有多少錢 | `bank_txn` 累計（銀行說了算） | `ledger` 算出的餘額若跟 `bank_txn` 不同＝「未對帳」警示，不是兩個數字並列 |
| 還欠銀行多少 | `loan_schedule` 剩餘本金（經 ledger 還款沖銷） | — |
| 這個月該發多少薪 | `payroll_run` | 分潤頁的試算只是「輸入」，定案以 payroll_run 為準 |
| 飯店欠我們多少 | `hotel_recon` | — |
| 損益表 | **由以上組合算出，沒有任何一格可手填** | 手填就會跟現場數字對不上 |

**關鍵規則：成本總覽的「廠商月帳」現在是自填金額，這就是未來最大的「各算各的」風險點。** 建議：財務中心一上線，就把那格改成讀 `ap_invoice`，並在成本總覽裡同時顯示三個名字清楚的數字——**進貨額（叫貨單）／應付額（月結單）／已付額（銀行）**，加一欄差異。三個數字本來就會不同（送貨差、折讓、付款時差），重點是名字不能混。

### 2.5 沿用 accounts／ledger 概念是否合適？

**結論：概念合適、欄位要改、資料位置要新建。**

| 面向 | 藍圖現況 | 餐飲集團要改成 |
|---|---|---|
| 核心觀念（轉帳≠費用、帳戶餘額＝期初＋進−出） | ✅ 對，直接沿用 | — |
| `accounts.type` bank/company/cash/petty/loan | ✅ 夠用 | 加 `store`（GD／AB／集團共用）欄；加 `hotel_receivable` 型別或用 counterparty 處理 |
| `ledger.cat_id`＝工程大項、`is_cost`＝算不算工程成本 | ❌ 工程概念 | 改成 `account_code`（會計科目：食材／人事／租金／水電／利息／稅金…）＋`store`＋`cost_center`（可選） |
| `ledger.vendor` 文字 | 太弱 | 改 `counterparty_type`（vendor／employee／hotel／bank／tax／other）＋`counterparty_id`（接物料庫廠商主檔、夥伴名冊） |
| 子帳連結 | 沒有 | 加 `ref_type`／`ref_id`（ap_invoice／payslip／loan_schedule／hotel_recon／tax_doc），這是「不各算各的」的技術保證 |
| 對帳 | 沒有 | 加 `bank_txn_id`、`status`（draft／confirmed／reconciled）；月結後 `locked_period` 關帳不能再改 |
| 稅 | 只有 `invoice_no` | 加 `tax_type`（應稅／零稅／免稅／無發票）、`tax_amount`、`tax_period` |
| 憑證 `receipts` | ✅ | 沿用，接 /prep 文件庫的私桶 |
| 資料位置 | 主 App `pm_fin_*` 依空間前綴 | /prep 另建 `sp_finance_pm_fin_*`，**不要兩邊共用同一把 key**；主 App 舊帳若有價值，做一次性匯入 |
| 權限 | 主 App「看金額」旗標 | /prep 要**伺服器端守門**（像物料庫 `me` 守門成本敏感那套），不能只靠藏分頁；薪資單再多一層「只看自己」 |

### 2.6 建議的建置順序（每步都能單獨上線）
1. **銀行明細上傳＋帳戶餘額**（`bank_txn` ＋ `accounts`）— 兩週可見成果，老闆最想看的是「錢在哪」。
2. **應付貨款**（`ap_invoice` 接叫貨單、取代成本總覽自填月帳）— 把最大的資料不一致風險先拆掉。
3. **貸款主檔＋排程**（小，一天）。
4. **薪資**（最敏感，權限最重，等 1、2 穩了再做）。
5. **飯店對帳**（等張良確認對帳方向）。
6. **401 工作底稿**（靠 2 的發票欄位累積兩個月資料後才有東西可出）。
7. **損益表／現金流預測**（全部接上才有意義，不要先做）。

## C. 我仍反對、老闆一定要知道的一點

**不要在這一步走「雙分錄／總帳中台」路線**（甲：ledger_entries/ledger_lines、資產負債表；乙：財務核心中台＋總帳勾稽中心）。
理由：張良要的是「用最少力氣把事情管好」，不是建一套會計系統。雙分錄每一筆都要對科目，沒有專職會計維護，三個月後就沒人記帳、報表全停；記帳士那邊本來就有正式帳。正確定位是**管理帳**：單式 ledger＋子帳（AP／薪資／貸款／飯店／發票）＋銀行對帳，就足以產出老闆要的餘額、應付、損益、現金流與 401 底稿。等這套跑穩一年、資料乾淨了，再決定要不要升級雙分錄，那時成本只是多一個轉檔，不是重做。
