### §9 八個問題審查

#### 1. 儲存：KV（pm_documents）夠不夠？何時切換？
- **結論**：第一期點數流水**絕對不能**走現有 KV 一筆一檔＋單一大索引檔；會員主檔可先暫留 KV，但流水與兌換必須立刻開 Supabase 真實關聯表。
- **理由／做法**：
  - `pm_member_idx` 把數千人塞在單一 JSON，高頻讀寫時極易產生 Race Condition（後寫覆蓋前寫）與 Vercel Payload 上限問題。
  - 點數牽涉金錢與稽核，KV 無法執行 `SELECT SUM(pts)`、交易鎖（`FOR UPDATE`）與唯一約束。
  - **切換做法**：保留設定（`pm_member_cfg`）走 KV，立即用 Supabase Migration 開三張真表：`members`、`member_point_logs`（流水）、`member_redemptions`（兌換單）。省力且徹底免除未來幾十萬筆流水時痛苦的非同步搬遷。

#### 2. 點數正確性：漏洞與冪等鍵
- **結論**：「流水加總再回寫餘額快取」在 Serverless 無鎖狀態下必定因併發而算錯，退款與作廢亦缺乏狀態機保護。
- **理由／做法**：
  - **漏洞防範**：餘額快取回寫必須透過 Postgres RPC（Function）在單一資料庫 Transaction 內執行（Atomic update），嚴禁前端或 Node 端讀出舊餘額再算。
  - **必備冪等鍵（Idempotency Key）**：
    - 團單結案入點：`idempotency_key = "EARN_GORDER_" + orderId + "_" + uid`
    - 現場入點：`idempotency_key = "EARN_POS_" + storeId + "_" + posTxNo`
    - 兌換扣點：`idempotency_key = "REDEEM_" + redemptionId`
  - **退款／作廢**：點數不得更動原流水，必須反向寫入一筆 `kind='refund_rollback'` 流水；若會員點數已被扣成負數，允許負餘額並在卡片標示警示。

#### 3. 防弊機制缺口
- **結論**：現有設計防了客人端，但完全忽略了「店員端內部作假」與「重複核銷」的時間差。
- **理由／做法**：
  - **防店員洗點**：店員手輸金額給點必須設定單筆上限（例：單筆滿 3,000 元或贈超過 30 點需主管 PIN 碼）；所有手動給點在 `/prep` 必須記錄 `staff_id`，且在日報表列出「手動給點排行榜」。
  - **防 QR 截圖轉傳**：動態 QR Code 內嵌 `uid:timestamp:HMAC-SHA256`，效期縮短為 60 秒（非 10 分鐘），避免被截圖轉傳多人排隊核銷。
  - **防重複兌換**：核銷 API 在 DB 端必須使用條件更新（Conditional Update）：`UPDATE member_redemptions SET status='used' WHERE id=? AND status='pending'`，成功回傳 row count = 1，避免同時多端兌換同一張券。

#### 4. 主鍵設計：LINE userId 為主、手機為輔的風險
- **結論**：以 LINE `userId` 當唯一主鍵是危險架構，應採用「內部 UUID」為系統主鍵，LINE ID 與 Phone 均為聯結鍵。
- **理由／做法**：
  - **風險**：客人封鎖再解鎖 LINE ID 不變，但換新 LINE 帳號、跨門市（若未來 A Beach 開不同 Provider）、或長輩沒有 LINE 只有手機時，系統會直接崩潰。
  - **做法**：建立 `member_id (UUID)`。當客人填入已存在的手機號時，後端觸發「帳號合併（Account Merge）」機制：將舊點數流水轉移至當前 `member_id`，並標記被整併的帳號，而非單純由店家手動排解。

#### 5. 現場 POS 無 API 下的運作可行性
- **結論**：店員手輸不可行（尖峰排隊必被客訴、店員必會作假）；改採「QR 登錄發票防偽碼」或「客人自掃小白單」更為穩健。
- **理由／做法**：
  - 喬亞 POS 會印出統一發票或小白單。
  - **省力低弊作法**：店員印出發票後，請客人開 LINE 會員頁「自行輸入發票號碼＋隨機碼」（或掃發票 QR），後端寫入佇列。店家打烊結帳時，由主管在 `/prep` 匯入 POS 日結 CSV 比對，或單純用發票號碼作唯一鍵防止重複登錄。若第一期堅持店員操作，店員必須在 `/prep` 輸入 POS 單號末 4 碼作存查稽核。

#### 6. 個資法合規最小功能
- **結論**：現有規格欠缺個資法第 3 條法定權利項目，需補齊宣告文案與自主功能。
- **理由／做法**：
  - **法規宣告**：LIFF 首次進入必須彈窗載明「蒐集機關（店名）、目的（餐飲服務/會員行銷）、類別（識別類 C001）、利用期間（營運期間/退會止）及地區」。
  - **最小功能**：
    - 查詢／閱覽／複製：現有會員卡頁即滿足。
    - 補充／更正：會員卡頁提供修正手機、統編與稱謂。
    - 停止利用／退會：後端提供「軟刪除」按鈕，將個資去識別化（清空姓名、手機），但保留交易流水並標記 `uid_anonymized`，以合規兼顧稅務與帳務保存。

#### 7. 第一期範圍建議與過度設計剔除
- **結論**：原規格 M1 範圍過大且重心失焦；「等級制度」、「自填統編公司」均屬第一期過度設計，應立即砍掉。
- **理由／做法**：
  - 第一期只需實現**「團訂累點」**與**「手動折抵」**闭環。等級門檻無實質回饋前只是裝飾；統編在團訂時已填，無須進會員卡設定。

#### 8. LINE 訊息成本控管
- **結論**：砍掉「到期推播」與「賺點 push」，改全走 Reply 免費通道與 LIFF 靜態展示，否則免費用量瞬間爆表。
- **理由／做法**：
  - **砍掉**：到期 30 天主動 Push（第一期點數有效期先設永久或 1 年，不用推）。
  - **改 Reply**：團體訂餐送出時若在 Webhook 50 秒回應視窗內，走免費 Reply；加好友歡迎詞走 Follow Event 的 Reply Token（免費）。
  - **不發通知**：賺點與兌換，客人本就在 LIFF 畫面操作，直接在「LIFF 頁面彈 Toast 或綠勾動畫」，不主動發送 LINE Push 卡片。將訊息額度 100% 留給收件匣真人客服與行銷推播。

### A. 你會改掉的設計（Why）

1. **改掉 `pm_member_idx` 索引檔架構**：
   - *Why*：單檔 JSON 索引在多用戶同時觸發（多人團訂完成）時必然覆蓋寫入，且每次查詢都耗費整檔傳輸頻寬。全面改用 Postgres Index。
2. **改掉「餘額寫在 Profile，每次重算」**：
   - *Why*：缺乏交易隔離機制時，若兩個訂單同時完成，會以同一基準加總，導致點數超發或被吃點。改為 DB RPC 事務處理。
3. **改掉 10 分鐘核銷碼**：
   - *Why*：10 分鐘足夠客人在 LINE 群截圖外流給他人代領。應縮短為 60 秒動態碼或現場單次性即時 Token。
4. **移除第一期的「會員等級（Tier）」**：
   - *Why*：兩家實體店初期無足夠行銷維運能量定義 VIP 權益，只徒增邏輯複雜度與客人疑惑。

### B. 漏掉的風險

1. **多人團購的點數爭議（拆單風險）**：
   - 規格訂「手打名字不賺點，主辦人拿共用」。實務上同事 A 會事後抱怨「我有 LINE，但主辦人幫我手打，我沒拿到點數」，導致店家常態性面臨客服人工補點壓力。
2. **退單與退款時的點數被提現（羊毛黨）**：
   - 團訂完成入點後，若隔天取消訂單並退款，而該主辦人已在門市將點數兌換炸雞，系統無「負點數追討」或「扣除退款金額」規範。
3. **門市離峰作弊**：
   - 店員無 POS 串接下自開 `/prep`，拿朋友的手機號虛報消費金額狂洗點數換免費用餐。
4. **LINE 封鎖流失率（Churn Rate）**：
   - 若每筆訂單完成都傳送多張計價圖與點數通知，高頻推播將導致封鎖率大增；客人一旦封鎖官方帳號，系統便失去與該會員唯一的主動聯繫管道。

### C. 第一期最小範圍（MVP 你的版本）

**目標：7 天內上線，專注於「團購閉環」與「門市最小可用」，技術架構一次到位不重構。**

1. **資料層（底層一次做對）**：
   - 放棄 KV，開 Supabase 三張表：`members`（以 UUID 為 PK，含 line_user_id、phone 欄位）、`member_point_logs`（流水表，含 idempotency_key）、`member_redemptions`。
2. **會員觸發點**：
   - 僅保留兩個：LIFF 團購點擊自動建檔、現場店員輸手機號建檔。拿掉 Follow 自動建殼（沒留資料的殼無價值）。
3. **賺點機制**：
   - 僅綁定「團體訂餐 `done`」：系統自動給主辦人及有帶 LINE 身分者入點（入點走 RPC，有冪等鍵）。
   - 現場消費：先僅供主管權限以人工 `/prep` 補登，不全面開放外場亂輸。
4. **用點機制**：
   - 砍掉複雜的獎勵商品庫存與核銷碼。第一期只做「團單直接折抵」與「門市折抵現金」（例：1 點折 1 元）。
   - 兌換方式：店員在 `/prep` 搜手機號，直接點擊「扣除 N 點折抵 N 元」。
5. **通知精簡**：
   - 砍掉所有賺點 Push。所有點數異動均靜態呈現在 LIFF `/member` 頁面中，只有在收件匣成立訂單時順帶夾帶點數資訊（0 元推播成本）。
