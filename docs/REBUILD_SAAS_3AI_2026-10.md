## 先講結論

**方向對，但不要把「先換 Next.js」當成「先打好地基」。**

真正的地基是：
- **誰擁有程式、資料和帳號。**
- **四套資料怎麼對應、哪套才是正式來源。**
- **公司、分店、使用者、顧問與權限怎麼分。**
- **金流怎麼防重複、資料怎麼備份、出事怎麼退回。**

我的建議是：

> **先盤點與取得控制權 → 定義共同地基 → 建新產品骨架 → 分模組搬入 → 驗證後逐步切換。**

不是先把四套拼成一大包，也不是停掉開發、把全部畫面重寫完才開始整合。

另外，這份審查以你提供的查證結果為依據；**我沒有實際看過四套完整程式、資料庫政策和正式環境紀錄**。下面會把「事實」與「尚待驗證的推測」分開。

# Q1. C1～C13 逐條檢核

### C1：畫面＋GitHub 程式碼不足以完整複製
**判定：正確。**

還要取得：
- 資料庫結構、資料、函式、觸發器、RLS 政策。
- Storage 檔案及其權限。
- 部署環境變數、排程、網域、OAuth 回呼網址。
- LINE、付款、信箱、POS 等外部服務設定。
- **實際跑在其他地方的程式**，例如 M1 腳本、Apps Script、未入 repo 的 gops-api。

補充：**有金鑰，不等於有帳號所有權。**產品要能長期營運，帳號歸屬與管理權比拿到一串密碼更重要。

### C2：Supabase 仍需鑰匙；邀進專案或拿 DB 密碼才能完整匯出
**判定：部分正確。**

正確的是：
- 前端使用 Supabase API，需要相應的 API key；連資料庫則需要資料庫連線授權。
- 前端 anon key **不是完整備份或管理權限**。

需要修正：
- anon key 能讀到什麼，要看資料表授權、RLS 和呼叫者身分；**不保證能抓到全部資料**。
- 「權限全開」反而是資安警訊，不是方便搬家的合理狀態。
- **DB 密碼不能單獨保證完整匯出 Storage 檔案、Auth 設定、Edge Functions、部署機密與外部登入設定。**
- 邀進專案也要確認給的是什麼角色、是否具有所需操作權限。

建議取得正式授權後，**分別備份資料庫、Storage、Auth／登入設定、Functions 與部署設定**。不要把資料庫備份誤當成整套系統備份。

### C3：複製與搬进 GD 不同；搬入等於重寫，零誤差靠並排比對
**判定：部分正確。**

- 複製與整合確實不同。
- 但不一定全部重寫：Belle 的 React 元件、計算邏輯或 API，**拿到原始碼與授權後可能可以沿用**。
- 並排比對必要，但**不能保證零誤差**。

除了畫面和數字，還要驗：
- 權限、歷史資料、錯誤處理。
- 日期邊界、退款、撤銷、重複提交。
- 銀行與帳務對帳結果。

**畫面看起來一樣，不代表系統行為一樣。**

### C4：Belle 慢說明框架不保證快；可能是讀資料或冷啟動
**判定：部分正確。**

「框架不保證快」正確；但慢的原因目前未查證。

首頁 curl 的 3 秒，不能直接代表分頁切換速度，也不能確認冷啟動。應量：
- 點分頁到可操作的時間。
- API 耗時、資料庫查詢耗時。
- 是否重複請求、一次下載過多資料。
- 首次與後續載入差異。

**先量再改，不要因為猜冷啟動就換架構。**

### C5：GD 延遲主因是 KV 整包讀、超大單檔、快取不足
**判定：部分正確。**

這些是**值得優先調查的嫌疑點**，不是已證實的主因。

- 整包 JSON 可能增加傳輸、解析與更新成本。
- 大檔案主要增加維護風險；不代表每次請求都執行全部內容。
- 金流、權限、餘額不能為了快而隨便快取。

要用實測確認：API 耗時、外部服務耗時、資料大小、查詢次數與錯誤率。

### C6：Next.js＋TypeScript＋Supabase 多租戶等架構，可用 5～10 年
**判定：部分正確。**

技術方向合理，但不是唯一選擇，也不能承諾壽命。

需要補正：
- `company_id` 要配合會員關係、分店歸屬、資料庫約束與 RLS，**不是每列加一欄就完成隔離**。
- 全域字典等共用資料，不一定需要 `company_id`。
- Email／Google 與 LINE 的登入整合難度不同；**LINE 不能當成勾選一個選項就完成**。
- 背景排隊要有重試、防重複、失敗告警。
- 綠界定期扣款須確認適用產品、特店資格、合約與付款失敗處理。
- AI 用量管制之外，還要防止把甲公司的資料送進乙公司的回答。

「可持續演進很多年」合理；「這套保證 5～10 年不用大改」不合理。

### C7：要賣給客戶，所以推翻「/prep 不換框架」
**判定：部分正確。**

可以重開架構討論，**但商用不等於必須換框架**。

真正改變的是多租戶、安全、維運與交接需求。可以：
- 舊 `/prep` 暫留自用。
- 新產品採新架構。
- 再逐步搬入成熟功能。

不必為了成立商用產品，先重寫所有內部頁面。

### C8：漸進替換，不一次全部重寫
**判定：正確，備援方式要補強。**

「舊頁留 1～2 週」不是充分的退路：
- 新系統開始寫資料後，舊系統是否讀得懂？
- 退回時，這段時間新增的交易怎麼處理？
- 新舊排程會不會各自推一次 LINE、記一次帳？

**要驗證資料與副作用的回退，不只是保留舊網址。**觀察期也要涵蓋相關營運週期，例如月結。

### C9：一個 App 只用一種框架；資料與後端可混
**判定：部分正確。**

- 長期統一主要前端技術，有助維護。
- **技術上不是只能一種框架**；過渡期不同路由用不同技術很常見。
- 資料層與後端可混，但要清楚定義資料主來源與職責。

JSON 適合部分設定；**涉及金額、點數、交易狀態與權限的關鍵資料，不宜只靠可覆寫的整包 JSON。**

### C10：另做顧問產品，自家兩店當第一個客戶
**判定：正確。**

這是好的產品邊界，不代表要複製一套程式另養。

建议：
- 同一套產品核心。
- 自家資料按實際公司與分店關係建模。
- 工程專案、老闆私人管理等功能，不必全部對客戶開放。

**自家使用也要走正常客戶權限，不能靠超級管理員掩蓋問題。**

### C11：客製設定、顧問指派、模組開通要先設計
**判定：部分正確。**

三者確實應在初期設計，但：
- 「永遠不為單一客戶寫程式」太絕對。可以做可重用擴充，避免每家分叉一套。
- 一開始就做萬用自訂欄位與流程引擎，可能把產品做得過度複雜。
- 模組開通不能只控制選單，**API、匯出、背景任務也必須檢查**。
- 顧問指派要有到期、撤銷、操作紀錄及服務範圍；顧問不應預設可看全部個資、薪資或金流。

### C12：阿桑資料庫底子較扎實，接近商用等級
**判定：部分正確。**

有真表、migration、RLS，是較好的基礎。

但 **587 支 migration、使用 SECURITY DEFINER，不是品質證書**：
- SECURITY DEFINER 若權限、參數或 `search_path` 設定不當，可能繞過保護。
- 已知高風險 bug 尚未排除。
- gops-api 不在交付包。
- 與 EM 共用專案的隔離仍未確認。

可以參考，**目前不能據此認定接近商用安全標準**。

### C13：阿桑交付不完整，需取得 repo、腳本並請小夏開權限
**判定：部分正確。**

缺交付的判斷正確，但：
- repo 不一定包含 gops-api，應列為独立交付項目。
- 还缺 Storage、帳號歸屬、排程設定、實際部署版本等。
- 不應直接索取整個 EM 專案所有資料；**要先確認授權範圍與個資，再匯出相關部分**。
- `public.profiles` 共用，搬走 ops 時不能直接刪掉或重建，否則可能破壞 EM。

**有條件同意。**

同意先建新產品骨架；不同意先全面重寫畫面。

先完成資料、身分、權限、備份與交易規則，再決定前端。Next.js 可以選，但**不是地基本身**。

### P2：先改地基再合併，還是先合併再改地基？
**不同意「沒差」。順序有明顯差別。**

- **先把四套程式硬併，再改地基：**很容易重做兩次，還把身分和資料衝突帶進新系統。
- **先把全部舊功能重寫完，再整合：**也不佳，因為還没理解另外三套資料，可能先做錯模型。

正確順序是：

> **先盤點四套 → 定義共同地基 → 建最小骨架 → 每次整合一個模組。**

每搬一個模組，同時完成資料、權限、介面和驗收。不是「先全部改完」或「先全部合完」二選一。

### P3：三套全部併進 GD
**有條件同意。**

同意統一產品入口與資料協作，**不建議四套全部搬入同一個程式庫、同一套資料庫後才算合併**。

逐模組決定：
- 重複的：擇一為正式來源。
- 成熟且值得保留的：整合。
- 暫時外部運作較安全的：以 API 串接。
- 不需要的：封存。

例如 EM 已有唯讀 API，初期可先維持同步；不必為了「全部併入」立刻重建包場系統。

### P4：直接切割掉舊主 App
**不同意直接切掉；同意有計畫退役。**

它仍有資料、近期仍有修改，代表不能視為空殼。

先確認：
- 還有哪些使用者與正式流程？
- 財務內帳和工程資料是否已完整移轉？
- 有沒有部署、排程、共用套件或 API 依賴？

通過驗收後再停止寫入、改唯讀、封存，最後移除入口。

### P5：/prep 改名 /ops
**有條件同意，但低優先級。**

目前已 rewrite 到 `/ops/index.html`，主要是入口整理，不是架構改造。

要保留相容性：
- PWA 啟動網址、Service Worker、快取版本。
- LINE 圖文選單、書籤、通知連結。
- 登入回呼、舊路由與深層連結。

阿桑也叫 ops 本身不是技術衝突，但兩套入口並存可能讓人登入錯地方。**先定產品名稱與正式入口，再改網址。**

### P6：以「改一次、合併、未來販售」為目的
**有條件同意目的，不同意承諾只改一次。**

可以做到：
- 避免明知要丟掉的短期重工。
- 多租戶與權限一開始納入。
- 用可演進的模組降低後續改動成本。

不能合理保證：
- 所有需求一次猜對。
- 所有資料一次搬完。
- 架構以後不再調整。

**應改成「地基先想清楚、分次搬、每次有驗收與退路」。**

# Q3. 建議完整執行順序與驗收標準

## 階段 0：先保護現在的營運
- 暫緩非必要新功能。
- 先處理已知高風險 bug：重複通知、錯誤更新、金額口徑不一致。
- 備份 KV、Supabase、Storage、程式與部署設定。
- 記錄目前正式版本及外部排程。

**驗收：**
- 備份實際還原到隔離測試環境成功。
- 測試環境不會推真 LINE、寄真信、扣真款。
- 正式環境的排程與部署位置有完整清單。

## 階段 1：取得四套的完整交付與權利
建立交付清單：
- repo、對應部署版本、授權。
- 資料結構、函式、政策、資料與檔案。
- gops-api、M1 腳本、Apps Script、Edge Functions。
- 外部帳號、管理權、環境變數名稱與安全交付方式。

**驗收：**
- 每個正式流程都找得到程式、資料來源與執行位置。
- Belle 的資料庫與後端不再停留在推測。
- 未能取得的項目有明確處置：暫留、替代或不納入。

## 階段 2：定產品邊界與資料責任
先畫一張「誰負責什麼」表：
- 公司／分店。
- 使用者／員工／顧問／消費者。
- 訂單、包場、收款、退款、總帳、會員點數。
- 各模組正式來源與同步方向。

特別訂出：
- 營業日、時區、跨午夜、月結口徑。
- 金額、手續費、訂金、收入認列規則。
- 財務結帳後能否修改，以及更正方式。

**驗收：**
- 每一類關鍵資料只有一個正式主來源。
- 公司與分店關係確定。
- 同一筆交易在各報表的計算方式可解釋、可對帳。

## 階段 3：建最小商用骨架
先做，不急著搬滿功能：
- 登入與身分對照。
- 公司會員、角色、顧問指派。
- 模組開通。
- RLS 與後端授權。
- 操作紀錄、備份、錯誤告警。
- 開發／測試／正式環境分離。

**驗收：**
- 用至少兩個測試公司驗證，不能跨公司讀、寫、匯出或取檔。
- 猜網址、改請求參數也不能越權。
- 顧問撤銷指派後立即失去存取權。
- 管理金鑰不出現在前端。
- 能撤回一次部署。

## 階段 4：做一個小型、完整的搬遷試點
選擇：
- 範圍小。
- 資料歸屬清楚。
- 可以停用退回。
- 暫不涉及不可逆的扣款或帳務寫入。

不要第一個就搬全部總帳、會員點數或所有 LINE 自動流程。

**驗收：**
- 從畫面、API 到權限完整走通。
- 遷移可重跑，不會越跑資料越多。
- 筆數、欄位、附件與權限皆核對。
- 使用者實際操作通過。
- 回退演練成功。

## 階段 5：分模組遷移
大致可按依賴關係安排：
1. 基礎資料與低風險營運模組。
2. 報表唯讀比對。
3. 排程與通知。
4. 訂單、金流、點數、帳務等高風險寫入。

每個模組都走：
**試搬 → 比對 → 使用者驗收 → 切換寫入 → 觀察 → 退役舊功能。**

**驗收：**
- 財務：逐筆及總額對帳，差異皆有原因。
- 通知：重試不會造成重複發送。
- 資料：新增、修改、刪除與撤銷均驗證。
- 明確知道切換後誰唯一負責寫入。

**不要讓新舊兩套各自自由寫同一份業務資料。**

## 階段 6：自家正式試營運，再找外部試點
- 自家兩店走正常權限。
- 驗證相關完整營運週期，財務功能包含月結。
- 再引入少量、需求單純的外部客戶。
- 完成收費、客服、資料匯出、解約與事故處理流程。

**驗收：**
- 沒有未解決的跨公司洩漏或重大帳務差異。
- 客戶開通與離場不靠手改資料庫。
- 有實際演練過的備份還原與事故聯絡程序。
- 成本、用量與顧問服務範圍能追蹤。

# Q4. 最容易出大事的風險

### 1. KV 搬真表，不只是把 JSON 拆欄位
可能藏有：
- TTL 到期資料、歷史格式、缺少 ID。
- 一份資料分散在多個 key。
- 同時更新造成覆蓋。
- 點數只有餘額，沒有可核對的異動紀錄。

**對策：**盤點實際 key 與資料版本；建立穩定 ID、來源對照表、重複處理規則及遷移核對報告。無法補回的歷史紀錄要明確標示，不能假裝完整。

### 2. 財務名稱相同，意思可能不同
「營收」「收款」「入帳」「包場訂金」可能不是同一件事。

若直接合併，畫面能跑，帳卻可能錯。

**對策：**由你確認業務口徑；帳務更正保留軌跡，不隨便覆蓋已結帳紀錄。稅務與帳務規則需要相關專業人員確認。

### 3. LINE DD 與 webhook 切換可能重複執行
LINE webhook、排隊重試、舊排程，都可能重複觸發。

**對策：**
- 驗證 webhook 簽章。
- 用事件識別碼等機制防重複處理。
- 明確切換唯一正式接收與執行路徑。
- 正式推播與測試推播隔離。
- 先比對「會做什麼」，不要讓測試真的扣款、加點或推訊息。

另需分清 **LINE Login 與 Messaging API 的帳號、channel、provider 關係**，不能假定不同來源的 LINE user ID 一定可以直接合併。

### 4. 四套登入不能靠同名或同 Email 自動合併
同一人可能有多種登入；同名也可能是不同人。

**對策：**
- 建立新舊身分對照。
- 重要帳號經使用者驗證或人工確認。
- 區分消費者、員工、公司會員及顧問。
- magic link 要檢查期限、用途與重複使用風險。

### 5. 阿桑與 EM 共用 Supabase：最大的權限地雷
分成 `ops`、`gops` schema，**不等於專案資源、管理權或安全邊界已分開**。

可能共用：
- Auth、profiles、Storage。
- 高權限金鑰、函式與資料庫資源。
- 備份、付費帳號與停用風險。

**對策：**先確認權利與依賴，再決定保留或拆分；不能搬走 ops 時順手改壞 EM。邀請進專案，也不等於取得使用全部資料的合法權利。

### 6. 程式碼與資料所有權
朋友提供程式，不代表已授權你修改、轉售、再授權。

**對策：**書面確認：
- 程式、資料、網域及服務帳號歸屬。
- 商用、修改、轉售與維護權。
- 開源及第三方元件授權。
- 對方退出時如何交接。

### 7. 個資與 AI 使用
員工薪資、會員電話、預訂資料、LINE ID 都可能涉及個資。

**對策：**
- 確認蒐集目的與新產品使用範圍。
- 最少存取、保留期限、離職／解約撤權。
- 不把正式個資整包貼進 AI 審查對話。
- AI 服務先做資料範圍限制與遮罩。
- 委外、跨境處理及事故義務請台灣法律專業確認。

### 8. 停機不只發生在 Vercel
M1 休眠、網路斷線、憑證過期，都可能讓抓取停止。

**對策：**
- 重要排程不只依賴單一個人電腦。
- 每個同步流程顯示最後成功時間，逾時告警。
- 定義可接受停機時間、可接受資料損失範圍與人工替代流程。

### 9. 「只有 AI 寫程式」缺少獨立把關
Claude 寫、其他 AI 看，是有幫助的，但大家可能基於同一份錯誤假設互相認同。

**對策：**
- 正式搬金流、多租戶上線前，找真人做有範圍的資安與資料庫審查。
- 讓實際使用者驗收，而非只看 AI 說測試成功。
- 每次發版保留測試證據、變更與回退方式。

### 10. 做成顧問產品後，報表錯誤會變成服務責任
除了程式問題，還有：
- 客戶依錯誤數字做經營決策。
- 顧問誤看別家資料。
- AI 將推估說成確定事實。

**對策：**報表標示來源、更新时间及計算口徑；重要建議可追溯到資料，區分 AI 草稿與顧問確認內容。

# Q5. 有沒有比 Next.js＋Supabase 更適合？

**有可能。對你們而言，我會把「React＋Vite＋TypeScript＋Supabase」列為同等候選，不會直接宣布 Next.js 勝出。**

| 方案 | 適合你們的地方 | 主要代價 |
|---|---|---|
| **Next.js＋TypeScript＋Supabase** | 前後端可在同一專案；適合產品官網、公開頁與登入後功能並存 | 伺服器／瀏覽器邊界、快取與部署行為較複雜 |
| **React＋Vite＋TypeScript＋Supabase，搭配明確後端 API** | 內部儀表板通常不需要 SEO；結構較單純，現有主 App、EM 也有相關基礎 | API、背景任務與登入流程要另訂清楚 |
| **保留現有 HTML，逐步模組化＋Supabase** | 短期成本低、現場變動少 | 長期多人維護、型別檢查與測試較辛苦；適合作為過渡 |
| **Django／Laravel＋PostgreSQL 等完整後端框架** | 成熟管理後台、權限、工作排程與交易處理能力 | 現有程式沿用較少；一人 AI 開發需重新建立整套熟悉度 |

### 我的選擇原則

- **若主要是登入後的餐飲管理、報表與顧問工作台：**
  - 優先考慮 **React＋Vite＋TypeScript＋Supabase**，不必為了商用強上 Next.js。
- **若同時要大量公開頁、客戶入口、伺服器渲染與同 repo 後端：**
  - **Next.js＋TypeScript＋Supabase**合理。
- 不論哪種：
  - 關鍵寫入要有可靠的交易、權限與防重複機制。
  - 高權限金鑰只能放後端。
  - 使用者直連 Supabase 與否，都要驗證 RLS。
  - 長時間工作不要硬塞在一次 HTTP 請求中。
  - LINE 整合、台灣付款與餐飲帳務，都不會因選了某個前端框架就自動解決。

**目前不建議為了「更專業」同時增加多套框架、微服務、自架資料庫和大型流程引擎。**你們最缺的是清楚邊界與可驗證的操作，不是更多技術名詞。

### Q1. 逐條檢核 Claude Code 的說法（C1~C13）

*   **C1：正確。** 系統不僅是畫面與原始碼，環境變數、DB 結構、檔案儲存（Storage）、排程（Cron）缺一不可。
*   **C2：正確。** 前端使用的 `anon key` 受 RLS 限制且無法撈取 Trigger/Function 等結構定義，必須擁有 Supabase 專案 Admin 權限或直接連線 DB 取得 Superuser 密碼才能執行完整備份。
*   **C3：部分正確。** 方向對，但「照規格重寫」的說法略有偏差。Belle 的系統若本就是 Next.js + React，未來新架構若也是 Next.js，其組件與資料流**可以直接移植或重構**，不需要將 React 降級為 Vanilla JS 再重寫。
*   **C4：正確。** 換頁延遲通常來自伺服器冷啟動（Cold Start）、未做 SWR 快取、或每次換頁都重新向資料庫進行無分頁的連線查詢。
*   **C5：正確。** Vercel KV 存大 JSON 造成每次讀取頻寬與反序列化成本高；`mail-sync.js` 龐大邏輯造成 Serverless 啟動耗時；前端缺乏快取導致重複拉取。
*   **C6：正確。** 這是成熟 SaaS 的標準技術堆疊。Next.js + TypeScript + Supabase（多租戶 RLS）足以支撐 5～10 年的業務成長。
*   **C7：正確。** 「內部自用」追求速度可以將就，「對外收費販售」需要穩定的型別安全、多租戶隔離與標準化架構。
*   **C8：正確。** 軟體工程大忌是「Big Bang 砍掉重練」。漸進式替換（Strangler Fig Pattern，絞殺者模式）才能確保現場營運不中斷。
*   **C9：部分正確。** 「一個 App 畫面只用一種框架」是理想，但**在過渡期可以並存**（例如 Next.js 主路由下掛載靜態 Vanilla JS 頁面逐步替換）。「後端與資料庫可以混合使用」的判斷完全正確。
*   **C10：正確。** 自家營運充滿客製化邏輯與特殊流程，對外產品必須標準化。自家店應作為該 SaaS 的「第一號付費測試客戶」。
*   **C11：正確。** 多租戶千萬不能為單一客戶開分支（Branch）改程式。必須依靠 `tenant_id`、權限矩陣（Entitlements）與自訂設定表來驅動模組。
*   **C12：正確。** 阿桑的資料庫設計（RLS、RPC、migrations、Schema 切分）極具商業架構參考價值；但單檔 58,000 行 HTML 絕對不能照搬。
*   **C13：正確。** 阿桑與小夏的資料庫深度共用，若無完整 Repo、邊緣函式、M1 腳本與 DB Owner 授權，強行匯入極易發生遺漏。

### Q2. 逐條評估張良的提案（P1~P6）

*   **P1. 先改地基成 Next.js＋React：【有條件同意】**
    *   *理由*：方向正確，但**不要全站重寫才上線**。應先建立 Next.js 架構作為「外殼」，現有的 Vanilla JS /ops 頁面直接先掛載在 Next.js 的靜態目錄下，新功能或要整併的功能直接用 React 開發，逐步替換。

### Q4. 容易被忽略的「致命風險」防空洞

1.  **阿桑與小夏的 Supabase 專案「寄生」風險（最急迫）**
    *   *致命點*：阿桑的現場營運與 profiles 身分表直接開在小夏的 Supabase 專案裡。若小夏更改密碼、專案欠費被停權、或刪除資料庫，張良的兩家店營運會瞬間癱瘓。
    *   *解法*：**第一要務是「分家」**。請小夏匯出資料庫，建立張良自己的 Supabase 實例，將營運數據完全遷移出來。
2.  **LINE 機器人 DD 與 Webhook 衝突**
    *   *致命點*：LINE Messaging API 的 Webhook URL 只能設定一組。阿桑的系統有推播與 LINE 選單，GD 的 `line-webhook.js` 也有 3,100 多行。合併過程中若兩個後端同時接 Webhook，會造成訊息重複發送、狀態覆寫或回覆混亂。
    *   *解法*：必須先建立一個統一的「Webhook 分發入口」（Router），收到 LINE 事件後，依據訊息型態或使用者狀態分流轉發，切勿兩套系統各自監聽。
3.  **登入身分（Identity）衝突與 Session 踢除**
    *   *致命點*：GD 使用自己的驗證邏輯，阿桑使用 LINE 圖文選單 Magic Link，Belle 與小夏各自獨立。合併為單一系統時，若使用者的 Email 或 LINE UID 在不同系統對應的權限不同，會導致員工「登入後找不到店」或「看到不該看的薪資」。
    *   *解法*：以 Supabase Auth 為核心，強制以「LINE UID」或「工作 Email」作為唯一識別碼，並建立關聯表 `user_company_roles`（使用者-公司-角色關聯），登入後先選擇進入哪家店。
4.  **智財權與外部夥伴授權風險（商業化地雷）**
    *   *致命點*：若未來要將系統作為「餐飲顧問產品」對外收費，阿桑、Belle、小夏寫的程式碼與資料庫設計是否有明確簽署「職務發明 / 著作權轉讓協議」？若無協議，日後產品賺錢，任何一人主張程式碼版權侵權，公司將面臨法律糾紛。
    *   *解法*：在整併程式碼前，張良必須與三位夥伴簽署合約，明確約定過去所寫代碼之智慧財產權歸屬，或以顧問費/入股方式買斷授權。
5.  **M1 Air 本機腳本單點故障（SPOF）**
    *   *致命點*：阿桑系統仰賴一台放在特定地點的 M1 Air 執行 LaunchDaemon 排程爬蟲抓取 Eats365/NUEIP。若該電腦斷網、睡眠、重啟或硬體損壞，資料同步即刻中斷。
    *   *解法*：所有爬蟲與定時任務必須徹底雲端化（改寫為 GitHub Actions 排程、AWS ECS Fargate 或雲端定時 Worker），不可留在個人筆電。

### Q5. 架構選型評估：是否有比 Next.js＋Supabase 更適合的選擇？

#### 結論：**沒有。在「一人 AI 開發＋餐飲顧問 SaaS＋台灣市場＋LINE 生態」的條件下，Next.js + Supabase 就是目前的最優解。**

#### 為什麼不選其他組合？
1.  **為什麼不是 Laravel / Django？**
    *   傳統後端框架雖然內建健全的多租戶與後台，但對一人使用 Claude Code 開發來說，全端 TypeScript（Next.js）能讓前後端共用型別（Type Sharing）。AI 在撰寫單一語言（TS）時的上下文切換成本最低，出錯率遠低於「前端 React + 後端 PHP/Python」。
2.  **為什麼不是純 SPA（Vite + React）+ Node.js API？**
    *   SaaS 產品需要 SEO（外部銷售官網）以及極度安全的伺服器端環境變數管理。Next.js 的 App Router 能將「公開行銷頁」、「內部 SaaS 應用」以及「API 路由」完美整合在同一個專案中，免去管理兩個伺服器環境的負擔。
3.  **為什麼資料庫非 Supabase 莫屬？**
    *   **RLS（Row-Level Security）是多租戶神兵**：傳統資料庫做多租戶，工程師如果有一支 API 忘了寫 `WHERE company_id = ?`，客戶資料就會外洩；Supabase 可以在資料庫底層鎖死，就算前端寫錯，客戶也絕對看不到別人的資料。
    *   **LINE 生態整合迅速**：Supabase Auth 支援自訂 OAuth 與 OpenID Connect，能無縫整合 LINE Login。
    *   **台灣與亞洲連線品質**：Supabase 支援選擇 AWS 東京（ap-northeast-1）節點，搭配 Vercel 的 Edge 網路，台灣現場載入延遲極低。

#### 總結建議
張良老闆請把握核心戰略：**「先獨立資產、以 Next.js+Supabase 建新家、舊系統分批遷入、用 RLS 守住安全」**。切忌在一團混亂時盲目合併程式碼，先收攏權限與資料庫，才是最穩健的商用轉型之路。
