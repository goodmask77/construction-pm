請先讀完本文件，再檢查現有專案與 AGENTS.md，直接完成可執行的第一階段，不要只回覆計畫或做靜態示意頁。以既有 App 的架構、登入、權限、設計系統及資料庫為基礎擴充；不要未經檢查就另建一套 App、會員庫或身份系統。

本次文件是需求與建議實作規格，並未檢查你的程式庫、POS 接口、LINE 後台或既有廠商合約。以下資料表、API 名稱是邏輯設計，可依既有專案調整，但不得省略交易一致性與驗收要求。本文不代表任何功能已完成。

策略：核心會員、贈送優惠券、點數、活動、遊戲與數據自己掌握；支付、付費票券保障及外部銷售通路採購或串接。不是一次全做，也不是購買完整 12CM 功能的替代承諾。

## 1. 目標與成功定義

顧客由官方 LINE 打開 LIFF 會員中心，完成入會、領券、看點數、參與活動；店員在現有 App 掃碼核銷；管理者在同一 App 設定活動並檢視實際回訪。

主要目標：有效入會、首次核銷、重複消費及可歸因的活動貢獻。好友數、點擊及遊戲參加數只是過程指標。售券收款、核銷收入與活動新增營收不得混為一談。

多品牌能力採共用程式、隔離資料。品牌名以現有設定為準，可支援 GROUN:D 與 A Beach，但不得因為共用系統就合併兩品牌會員權益、訊息受眾、點數或行銷同意。

## 3. 架構與現況檢查

建議層次：顧客 LIFF 前台／既有員工 App → 有身份與權限檢查的服務 API → 資料庫與帳本 → 工作佇列 → LINE／POS／未來金流 adapter。

- 如果現有系統使用 Supabase，可重用 Auth、Postgres、RLS 與既有後端；若不是，不為本功能強制換技術。
- 券、點數與獎項變更須在受信任的伺服器交易中完成；禁止前端直接更新餘額或中獎結果。
- 金鑰放伺服器 secret，不能寫入前端、Git、匯出檔或日誌。
- 顧客與員工入口分開權限；無登入、跨品牌、跨門市的請求均在後端阻擋。
- 用 feature flags 分品牌啟用會員、活動與通知。測試會員及報表與正式資料可辨識且隔離。
- 工作佇列與 outbox 優先重用專案能力，避免為小流量引入不必要的微服務。

### 3.1 LINE 接入的必查項目

| 檢查項目 | CC 應做 |
|---|---|
| OA、Provider、Messaging API、LINE Login、LIFF ID | 記錄映射、管理權限與用途；不要猜 ID 或擅自重建 |
| 既有 12CM／其他服務 | 確認一般 webhook 或模組接法及可共存範圍 |
| webhook | 一般 channel 一個 endpoint；需要共用時先設計事件分流，不能覆蓋現有服務 |
| UID | 同 Provider 的對應可一致；不同 Provider 必須另做驗證綁定，不用顯示名稱合併 |
| 身份驗證 | 後端驗 LINE token，檢查預期 client／channel、有效期與標準登入防護 |
| webhook 安全與可靠性 | 驗原始 body 簽章；事件去重；入列後快速回應；容許重送、延遲及亂序 |
| 發訊 | Reply 受 token 與事件條件限制；主動行銷用適合的發送方式並計成本 |
| 歷史與好友資料 | 不保證取回過往所有聊天或完整好友名單；以實際權限和接口為準 |

登入成功不等於已加好友；成為會員也不等於同意行銷。這三個狀態獨立保存。不同官方 LINE 也不能共用「已加好友」狀態。

## 4. 頁面與操作流程

### 4.1 顧客端 LIFF

| 頁面 | 必備內容 |

| 登入／入會 | LINE 登入、必要資料、服務條款與個資說明、獨立行銷選項 |
| 會員首頁 | 品牌、會員卡、可用券數、可用點數、近期到期項目 |
| 我的優惠券 | 可使用／已使用／已到期／已撤銷；細則與門市限制 |
| 優惠券詳情 | 效期、適用條件、核銷 QR；不可由顧客自行按完成核銷 |
| 點數紀錄 | 每筆增加／使用／到期／沖回與原因，顯示可用餘額 |
| 個人資料 | 可編輯欄位、生日修改規則、同意狀態、資料處理申請入口 |

會員中心必須手機優先。重用既有品牌視覺，按鈕清楚、錯誤可理解，不顯示內部技術名詞。狀態必須有 loading、empty、error、無權限及重試流程。

### 4.2 員工／管理者 App

新增「會員與行銷」區：總覽、會員、優惠券、點數、活動、推播、報表、設定；未開發項目隱藏或明確標記，不做假成功按鈕。

店員手機首頁保留「掃碼核銷」及「會員查詢」。核銷流程：掃 QR → 後端預檢 → 顯示優惠內容與限制 → 店員確認適用訂單／金額 → 原子核銷 → 顯示核銷時間與操作者。預檢成功不保證最終核銷成功，提交時重驗所有條件。

優惠若有限定品項或最低消費，P1 未接 POS 時必須標示「店員人工核對」，保留訂單參考與核對紀錄，不能宣稱自動驗證。會員 QR 與單張券 QR 要清楚區分。

角色建議：系統管理員、品牌管理員、行銷、門市主管、店員、分析唯讀。店員僅操作授權門市、必要會員資訊與限額內點數；不能匯出全品牌個資、改獎率或任意補券。

## 5. 資料模型：邏輯表與不變條件

既有等價表優先重用；下列為必要概念，不要求照名稱另開一套。

| 表／概念 | 主要欄位或約束 |

| brands / stores / staff_scopes | 品牌、門市、角色及授權範圍 |
| line_channels | brand_id、provider_id、channel_id、用途、secret reference |
| members / brand_memberships | 身份主檔與品牌會籍分離；品牌會籍唯一 |
| external_identities | provider_id＋line_user_id 唯一；與會員經驗證綁定 |
| consent_events | 目的、同意／撤回、政策版本、時間、來源；追加保存 |
| friend_status | channel＋身份、最近已知狀態及觀測時間；不能當絕對即時真相 |
| tags / member_tags / acquisition_sources | 來源與活動／門市關聯，避免覆蓋首次來源 |
| coupon_templates / template_versions | 券種、效期、門市、消費條件、發放限制、規則版本 |
| coupon_instances | owner_membership_id、版本快照、valid_from、expires_at、狀態、issue_key 唯一 |
| redemptions | coupon_instance_id 唯一成功紀錄、store、staff、order_ref、時間 |
| points_ledger / point_lots / allocations | 不可改寫流水、到期批次、使用分配、來源與反向交易參考 |
| orders / order_adjustments | 外部系統＋order_id 唯一；已付款、退單、退款等狀態及來源可信度 |
| campaigns / versions / prizes | 活動、規則快照、期間、獎項數量、成本上限 |
| participation_rights / draws | 資格來源、使用狀態、中獎結果；每個資格只對應一筆抽獎 |
| referrals / missions | 推薦者／被推薦者、歸因規則、有效交易與獎勵狀態 |
| outbox / webhook_events / jobs | 事件唯一鍵、狀態、嘗試次數、下次重試、失敗原因 |
| notification_jobs / deliveries | 受眾快照、模板版本、成本預估、發送結果；未知结果獨立狀態 |

所有時間儲存 UTC，活動、生日及報表以 Asia/Taipei 計算。有效區間統一為 start <= now < end；日期型到期於台北時間次日 00:00 失效。金額用整數最小貨幣單位與幣別，不用浮點數；點數用整數。

業務資料須有品牌範圍，伺服器從可信身份與授權取得範圍，不僅依前端 brand_id。必要索引包含品牌／會員／狀態／到期時間；列表分頁，不讓手機一次讀全部會員。

## 6. 會員、優惠券與點數規則

### 6.1 入會與生日

- 入會禮以「品牌會籍＋規則版本」去重；重新登入、重新加入好友或 webhook 重送不能重發。
- 生日禮以「品牌會籍＋當地年份＋規則版本」去重。生日修改不重置本年度領取資格。
- 生日資料可選填；2/29 非閏年預設 2/28 發放，寫在可設定規則及說明。發放排程可補跑但不能重發。
- 顧客隱私／行銷同意、身份綁定與資料匯出刪除請求需有處理流程；資料保留政策由營運確認，不擅自訂永久保留。

### 6.2 券的生命週期

issued（未到期且未使用）→ redeemed／expired／revoked；未到 valid_from 時顯示尚未生效。P2 轉贈另外記 ownership history，不靠複製券實現。

- 發券時固定規則版本與期限；後續模板修改不默默改變已發券權益。
- 核銷需要已授權員工、適用門市、有效時間及可用狀態；在資料庫交易內鎖定或條件更新。
- QR 使用不可預測的短期 token，不嵌明碼個資。截圖不等於可自行兌換；最終仍需授權店員與伺服器核驗。
- 斷網不得顯示成功或先離線核銷，顯示未完成並允許安全重試。
- 主管撤銷核銷須有理由與稽核；依券效期決定是否恢復可用，不刪除歷史紀錄。

### 6.3 點數帳本

- earn／spend／expire／reverse／adjust 都追加流水，不能覆寫總餘額來代替記錄。
- 使用時按最早到期批次扣點，保留 allocation；並發扣點不能讓可用餘額小於零。
- P1 不強制訂「每多少元一點」；規則可設定、正式發放預設關閉，先用測試規則驗證。
- 人工發點須金額或點數、訂單／來源參考、原因、操作者；同訂單重送不得重複發點。
- 退單回收已賺點數；如果已使用，記錄欠點／待處理差額而非刪改舊流水；可用點數最低顯示 0，後續賺點先抵欠額。此政策正式啟用前應由營運確認並告知會員。
- 取消兌點要按原 allocation 返還；原點數已過期不得自動延長，可用補償流程另發並留原因。
- 點數到期排程與手動使用使用相同交易規則，避免同一批點數又花掉又扣到期。

## 7. 遊戲與推薦引擎 P2

### 7.1 先做刮刮卡，再決定是否增加輪盤

流程：取得資格 → 後端一次消耗資格並抽獎 → 保留獎項庫存／成本 → 建立獎勵及 draw → 前端演出 → 顯示已保存結果。

同一 transaction／可靠工作流保證資格、庫存、結果與發券一致。重試同一 idempotency key 必須返回原結果；重新整理不能再抽。網路斷線後能查回結果。不得由前端 random 決定獎項。

建議以固定獎池槽位法實作：活動建立有限獎項及未中獎槽位，伺服器用安全亂數從剩餘槽位選取並原子扣除。所有獎品依保守估計成本預先受總預算約束；對外清楚說明數量及機會隨剩餘獎池變化，不宣稱固定機率。若改用權重抽獎，須另外定義缺貨時處理及機率揭露，不混用兩種模式。

活動狀態 draft → scheduled／active → paused → ended。暫停只停止新參加，既有合法獎券依原規則有效。開始後不可隨意改已承諾獎池或既有結果；修改走版本與稽核。

預设僅測試免費活動；付費抽獎、購買抽獎次數不在範圍內。促銷正式上線前確認適用活動規範與公告條件。

### 7.2 資格與防重複

可支援：每品牌會員每日一次、每活動一次、每筆有效消費一次。server 產生資格，唯一鍵涵蓋活動＋會員＋日期或訂單。額度限制在 DB 層原子執行。

可做請求頻率限制與異常提示，但不能保證一個 LINE 帳號就等於一位自然人。涉及高價獎勵，可另設經驗證手機或人工審核門檻，不能只靠裝置指紋判斷。

### 7.3 推薦好友

使用專屬推薦連結／代碼。記錄第一個有效歸因，明確排除自薦、既有品牌會員與重複歸因。分享成功不能等同朋友已加入。

預設規則草案：被推薦者完成入會及首筆有效付費消費後，等待可設定的退款觀察期才向雙方發券；不同品牌分別歸因。退單能撤銷未使用獎勵，已使用列異常，不偷偷刪紀錄。若未串 POS，需主管確認有效訂單，報表標示人工驗證。

### 7.4 任務集章

任務可為不同日期消費、指定門市或指定品類。用已驗證事件判斷，單筆訂單不得重複計數。品類任務必須有品項資料，沒有 POS 資料就不能假裝完成自動判斷。

## 8. 發訊與自動化 P2

券發入會員券夾與 LINE 通知是兩個流程：訊息失敗不撤銷券、不重發另一張券。後端先落地業務狀態與 outbox，再由 worker 發送。

通知需保留：channel、brand、member、event、dedup key、模板版本、預定時間、送出嘗試、結果與錯誤。由伺服器決定可發受眾與頻控。

- Marketing 與服務通知分類；行銷撤回者排除行銷訊息，其他通知仍按其適用依據和設定處理。
- 封鎖／不具資格者不承諾送達；API 接受不等於顧客已讀。
- LINE 計費與配額以當期官方規則為準；不能承諾 App 發送免費。
- Reply 只能在符合條件的事件中用；生日或排程不可假冒 Reply。
- 試發、正式受眾預覽、預估訊息量、頻率上限、安靜時段、取消排程都要具備。
- 重試依錯誤類型與退避；遇到發送結果不明，標 unknown，使用端點支援的 retry key／查詢機制處理，不能盲目重送造成重複訊息。
- 未填金額／次數上限時，正式大量推播預設不啟用。後台顯示配額、失敗與異常狀態。

## 9. API 契約與錯誤處理

下列為建議邏輯路由，可依既有命名調整：

| API | 職責 |
|---|---|
| POST /auth/line/exchange | 驗證身份並建立自家 session |
| GET /me/membership | 回傳當前授權品牌會籍 |
| GET /me/coupons、/me/points | 分頁券夾與點數流水 |
| POST /staff/redemptions/preview | 掃碼預檢，不消耗券 |
| POST /staff/redemptions | 帶 idempotency key，交易式核銷 |
| POST /staff/points/adjustments | 按角色與額度發點／調整，必填原因 |
| POST /admin/coupons/issue | 批次發券任務，逐會員去重 |
| POST /campaigns/{id}/draws | 後端驗資格、抽獎、發獎 |
| GET /me/draws/{id} | 斷線恢復取回原結果 |
| POST /integrations/line/{channel}/webhook | 簽章驗證及事件入列 |
| POST /integrations/pos/events | 驗證來源，處理訂單與退款去重 |

成功回應含 resource_id、status、server_time、必要餘額／結果；錯誤含穩定 error_code、可理解 message 與 request_id，不洩露個資。業務重複回傳原結果或明確 already_processed；已用券、過期券、門市不符、資格不足不可顯示一般成功。

冪等鍵依「品牌＋操作＋來源事件／請求」隔離，保存 request hash；同 key 不同 payload 必須拒絕，不能套用另一筆請求。

## 10. 報表與成效定義

| 指標 | 定義及限制 |
|---|---|
| 新會員 | 期間首次建立的品牌會籍，排除測試及重複 |
| 券核銷率 | 同一發券 cohort 已核銷數／成功發券數，標明觀察截止日 |
| 首次轉換 | 入會後首次有效交易；只有券核銷時另標「首次核銷」 |
| 回購率 | 指定 cohort 與觀察窗中至少第二次有效消費的人數／該 cohort 消費人數 |
| 推薦轉換 | 歸因新會員中完成有效首購者／歸因新會員 |
| 活動成本 | 已使用獎勵成本＋訊息＋必要變動成本，未使用獎勵另列承諾成本 |
| 活動關聯營收 | 有活動／券關聯的淨訂單金額，不直接叫新增營收 |
| 增量貢獻 | 有合理對照群或實驗設計才估算，標示假設與不確定性 |

同單多券只計一次訂單營收；跨活動可重疊歸因需明示，總覽去重。未串接 POS 的交易與客單資料標為缺失／人工來源，不能填 0 造成誤判。

## 11. 第一階段工作包與交付順序

| 工作包 | 實作 | 完成證據 |
|---|---|---|
| W0 盤點 | 現況、重用清單、外部接入風險 | inventory 文件及可執行 backlog |
| W1 資料基礎 | migration、品牌門市权限、身份映射、稽核 | migration 可在測試環境正確套用 |
| W2 入會 | LIFF 身份驗證、會籍、同意、會員卡 | 登入與重登入不重建會籍 |
| W3 優惠券 | 入會禮、生日排程、券夾、模板版本 | 去重、效期與補跑驗收 |
| W4 核銷 | 店員掃碼、預檢、原子核銷、主管修正 | 兩裝置並發僅一筆成功 |
| W5 點數 | 帳本、批次、扣點、到期、沖回 | 並發扣點及退款測試 |
| W6 可營運性 | 基本報表、匯出、監控、備份／恢復程序 | 權限與報表驗證、操作指南 |

W1–W6 不必等待全部外部接口開通才能開發。以 sandbox adapter 完成可驗證流程，真實接口阻塞逐項列出，不能將 mock 當已完成串接。

第一階段完成後再執行 P2：可靠訂單事件 → 共用資格／獎項引擎 → 刮刮卡 → 推薦／任務 → 分眾通知。不要在核銷與帳本未驗收前先堆遊戲動畫。

## 12. 必要驗收案例

以下驗證會影響會員權益、訊息成本與資料隔離，需自動化測試；UI 外觀以手機及桌機檢查，不寫只重述實作的測試。

| ID | 場景 | 預期 |
|---|---|---|
| A01 | 修改前端 UID、brand_id、store_id | 無法冒用／越權 |
| A02 | LINE token 無效／錯 channel／過期 | 拒絕建立 session |
| A03 | webhook 簽章錯誤、重送、延遲 | 拒絕偽造；真實事件最多一次業務效果 |
| A04 | 同會員重登入／重加好友／重跑入會事件 | 會籍與入會禮不重複 |
| A05 | 台北時間生日前後、2/29、生日修改、補跑 | 按配置發放且每年一次 |
| A06 | 同券兩裝置同時核銷 | 僅一筆成功，其他明確已使用 |
| A07 | 過期／未生效／撤銷／非適用門市券 | 全部拒絕核銷 |
| A08 | 預檢後券被另一人用掉、網路中斷重送 | 不二次核銷，能查回確定結果 |
| A09 | 點數並發扣點、到期與扣點同時發生 | 無超扣，帳本可重算一致 |
| A10 | 重複訂單／部分退款／全額退單 | 按已確認政策沖回且不重複 |
| A11 | 推播失敗但發券成功 | 券保留；重試不多發券 |
| A12 | 角色切換、跨品牌查詢、匯出 | 未授權資料不可讀取 |
| A13 | 活動只剩一個獎，多人同抽 | 庫存不負、成本不超、無重複資格 |
| A14 | 抽獎刷新／斷線／同 key 不同請求 | 原結果可恢復；不同 payload 被拒絕 |
| A15 | 自薦／舊會員／重複推薦／首購退款 | 不錯發或重發推薦獎勵 |
| A16 | 發送 timeout、429、重試與撤回行銷同意 | 不盲目重送、不對不合格行銷受眾發送 |
| A17 | 報表含測試、退款、同單多券 | 測試排除、退款扣除、營收去重 |
| A18 | 功能停用／備份還原演練 | 可停新活動且不毀損既有券與帳本 |

P1 必須通過 A01–A12、A17–A18 的適用部分；外部接口測試未完成明列阻塞。P2 上線前再通過 A13–A16。不能用純前端測試宣稱交易並發安全。

## 13. 上線、遷移與維護

- 既有資料先備份與盤點，不清空舊會員或直接覆蓋餘額。匯入以來源 ID 去重並保留來源；不能用姓名當身份鍵。
- 新舊系統並存時，明確指定券與點數唯一寫入來源，避免雙邊各發一次。資料映射未完成，不自動合併。
- 先 staging／測試 OA 驗证，再單品牌／單門市小流量啟用，最後擴大。
- migration 優先可相容擴充，提供回滾或前向修復計畫；停用 feature flag 不代表刪除資料。
- 監控 webhook lag、job 失敗、核銷錯誤、帳本差異、獎品庫存、訊息量；提供可追查 request/event ID。
- 定義例行備份與恢復責任，記錄至少一次測試環境恢復結果。不要只寫「有備份」。

以下不是阻止開發的理由：做成設定或採安全測試值。正式啟用前由管理者設定；不得當成已同意的商業條件。

| 設定 | 未確認時預設 |
