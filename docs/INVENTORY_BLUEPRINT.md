# 進銷存藍圖（INVENTORY_BLUEPRINT）v2 定稿

> 2026-07-18 張良與 AI（含 GPT/Claude 交叉檢視）多輪討論定稿。
> 核心一句話：**後台全系統只認一份物料主檔；POS 銷量×食譜只算「理論耗用」，實際庫存靠盤點對差；前台每個人只看「今天該做什麼」。**

## 三層分離（整套系統的操作哲學）

| 層 | 誰 | 做什麼 | 對應頁面 |
|---|---|---|---|
| 設計 | 張良＋AI | 物料主檔結構、單位換算、食譜關聯、警示條件、權限流程 | 藍圖/程式 |
| 管理 | 店長/主管 | 直覺打勾 keyin：盤點頻率、今日報價、選廠商、安全庫存、食譜維護 | 物料頁/報價分頁/產品卡 |
| 執行 | 現場員工 | 無腦照做：今日備料打勾、今日盤點填數字、驗收點選、耗損快記 | 每日工作（Today）＋驗收 |

> 管理者設定「什麼情況下要做什麼」，系統每天產生工作，現場只負責執行與回報。

## 核心資料模型：物料 vs 貨源（多供應商的解）

**「高麗菜」是一個物料；A/B/C 菜商的高麗菜是它的三個「供應選項（貨源）」。**
食譜、庫存、耗用只認物料層；比價換廠商只動貨源層，什麼都不裂開。

```
物料 ingredient（高麗菜, baseUnit=g, 盤點頻率, 安全庫存, 關鍵品項）
  └ 貨源 vendorItem（A菜商 20kg/箱 $800 → packToBase=20000 → $0.04/g）
  └ 貨源 vendorItem（B菜商 15kg/箱 $570 → packToBase=15000 → $0.038/g）←最低標綠
  └ 貨源 vendorItem（C菜商 散裝/kg $42 → packToBase=1000 → $0.042/g）
```

等級不同（一般/高山/特選）＝不同物料，不硬當同一項比。

## 核心公式

```
理論耗用 = POS 銷量 × 食譜用量          ← 只是「理論」，不是真實庫存
推算庫存 = 驗收入庫 − 理論耗用 − 耗損 ± 盤點調整（未來＋領用/半成品產出）
差異     = 推算庫存 − 實際盤點          ← 差異才是管理訊號（浪費/流失/配方不準）
明日備料 = 預估銷量 × 食譜 − 現有庫存   （第一版可用主管填預估份數）
成本     = 用料 × 最近實際驗收價 ＋ 包材成本；毛利 = 售價 − 成本
```

## 五條鐵律（修正版定稿）

1. **品項唯一**：食譜、POS、備料、庫存、貨源、叫貨全關聯同一個物料 ID，不掛名字。
2. **原始紀錄不可覆蓋**：進價、報價、食譜版本、驗收、耗損、盤點、庫存異動全部保留流水；**現值可以快取，但必須能從流水重算**（vendorItems.last / .quote 都是快取）。
3. **理論與實際分開**：POS×食譜只產生理論耗用；盤點是實際結果；兩者差異才是訊號。
4. **單位自動換算**：採購用箱、庫存用公斤、食譜用公克；管理者設一次 packToBase，現場用熟悉單位。
5. **警示必須可處理**：只推真異常（成本突漲/盤差過大/到貨不符/發票不符/備料連續不足/關鍵缺貨），點了直接進對應單據，不只顯示紅字。

## 報價 vs 進價（分開存，用途不同）

| | 報價（pm_quote_) | 進價（pm_price_) |
|---|---|---|
| 是什麼 | 廠商喊的價（未成交） | 驗收完成的實付價 |
| 來源 | 報價分頁 keyin（未來：LINE 讓 D 記） | 「完成驗收」自動寫 |
| 用途 | 比價選廠商（標最低，人點誰叫誰，不自動下單） | **成本計算唯一依據** |
| 快取 | vendorItems.quote | vendorItems.last |

## 三個落地咬人細節（實作必守）

1. **耗損快記不重複扣帳**：耗損快記是「解釋盤差的原因」，不是第二條扣帳線。實際庫存永遠以盤點為準；快記只說明「理論 vs 實際的差額裡，多少是已知報廢/員工餐/失誤」。兩邊都扣＝重複計算。
2. **POS 品項對應不能靜默**：POS 品名 ↔ products.posName 對應表人工建；對不上的 POS 品項列「未對應清單」常駐可見，絕不靜默忽略（否則新品耗用憑空消失，庫存慢慢飄）。
3. **警示門檻要有預設**：進價/報價變動 >15%（settings.priceAlertPct，可調）才警示，避免天天吵或永遠不吵。

## 首頁歸屬（範圍界定，防打架）

進銷存**不自建首頁**。今日備料、今天該盤的品項、缺貨提醒、到貨驗收，全部是**餵給每日工作系統（任務中心 Today）的工作來源**——物料主檔的盤點頻率＝模板，今天該盤的＝展開的實例，同一套機制。
⚠ 技術陷阱：TaskCenter 讀裸 key `pm_task_<id>`；供應鏈模組寫任務**不能過 K()**（會變 sp_supply_pm_task_ 沒人讀），要直寫裸 key。

## 盤點設計（防崩掉＝整套系統成敗關鍵）

- 頻率逐物料勾（物料頁）：每日／指定星期／每月幾日／不盤＋暫停；負責角色（內場收班…）；盤點單位。
- 執行端只顯示「今天該盤的幾樣」，填數字送出；**不顯示系統預估**（防照抄）；主管端才看理論 vs 實際差異。
- 只盤關鍵少數起步，不逼全品項——要求全盤兩週後就沒人數，假數字比沒數字更毒。

## 儲存架構

| 資料 | 存法 | Key |
|---|---|---|
| 物料主檔/貨源/設定 | pm_supply 整包（主檔低頻，量小） | `sp_supply_pm_supply` |
| 進價事件 | 逐筆，**決定性 id**（orderId_index，重按驗收冪等） | `sp_supply_pm_price_<oid>_<i>` |
| 報價事件 | 逐筆 append-only | `sp_supply_pm_quote_<rid>` |
| 食譜版本 | 逐筆 append-only（每存＝新版本；歷史報表取 ts≤當日版本重算，天然不變） | `sp_supply_pm_recipe_v_<rid>` |
| 未來：耗損/盤點/庫存異動 | 逐筆，異動類型枚舉預留：**驗收入庫/理論耗用/耗損/盤點調整/領用** | 未定 |

- 叫貨單 orders 上限 600 張會滾動；進價事件獨立存所以價格歷史不隨叫貨單消失。
- 已知限制：手動把叫貨單狀態下拉改「已到貨」**不會**寫進價事件——正式進價一律走「完成驗收」。
- 已知債務：pm_supply 整包兩人同時編輯可能互蓋（既存風險）；未來量大再拆 pm_ing_ 逐筆存（loadRecords 的 legacyKey 遷移機制是現成退路）。
- 單位鐵則：食譜用量單位鎖＝物料 baseUnit，不做 kg↔g 自動換算（深坑）；packToBase 沒填時成本顯示「未設換算」，**絕不當 0**（0 會讓毛利虛高，比錯更糟）。

## 不要做的事（第一版刻意不做）

全品項即時精準庫存、自動下單、批號效期全程追蹤、複雜需求預測、大量分析儀表板、每動作審批。
不讓任何新模組另存品名文字/自己算金額——一律掛物料 ID、共用 `src/supply/inv.js` 算法（同 lib/cost.js 精神）。
